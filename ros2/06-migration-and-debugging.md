# 从定位节点走到实船、迁移和调试

这页是简明回顾。扩写版分别沿旧驱动追设备反馈，再从收不到话题、方向反了、深度停更等现象追实际代码。[实船迁移详解](deep/08-ship-hardware-and-migration.md) · [按证据读故障和测试](deep/07-debug-by-evidence.md)

## 第 21 课 · 香橙派、飞控和执行器怎样分工

定位包计算“子船在哪里”。控制程序读取手柄或上游控制指令，给执行器输出信号。理解整船时，可以顺着每条链路分别问清输入、计算、通信接口和物理设备。

| 功能 | 源码中能跟到的链路 | 部署时要核对的连接 |
| --- | --- | --- |
| 母船手动推进 | 旧 `mz_usv/src/auto_pwm.cpp` 读 `/mother/joy`，从左右摇杆轴得到两路电调信号 | 对照实际使用的启动文件、两路接线、摇杆轴、指令超时和中位 |
| 缆绳长度 | 旧 `usv/src/motor.cpp` 与缆绳电机控制器串口通信，从编码器反馈计算缆长，再发布 `/sensor/cable_length` | 对照端口别名、通信设置、零点、换算比例和更新频率 |
| 母船飞控姿态 | 旧母船 MAVROS 入口读取飞控数据，航向节点订阅其 IMU 消息 | 核对板上实际运行的桥接入口、坐标约定、IMU 消息与安装方向 |
| 相对深度 | 新旧定位节点均从 `/sensor/relative_depth` 读值 | 已备份代码中找到订阅端，发布程序、设备、采样频率和深度参考点仍待确认 |

PWM 是 Pulse-Width Modulation（脉宽调制）。旧推进代码把手柄值转换为两路周期信号的脉宽，交给电调。电调也叫 ESC（Electronic Speed Controller，电子调速器）。左右推力差可以改变船的转向，实际左右方向要从电调、推进器接线和安装确认。GPIO 是 General-Purpose Input/Output（通用输入输出），是板上的引脚能力。理解原程序时，要区分“通用引脚编号”“硬件 PWM 通道编号”和“接口上的物理引脚号”。它们是不同的编号体系。

串口是连续收发字节的接口。应用要进一步定义字节如何组成数据帧、怎样校验、如何转换为米或角度。Linux 设备规则（udev 规则）可以根据设备属性创建一个稳定别名，例如旧电机程序使用的 `/dev/motor`。升级系统时，旧规则和通信参数可以作为核对起点。新系统要验证设备是否仍匹配、用户有无读写权限、引脚复用是否启用。飞控是独立控制器，可以提供姿态并承担平台控制功能。这个项目从代码能确认的母船航向链路走 MAVROS，另一条母船手柄链路走板端 PWM，飞控与实际推进电调的连接需实物确认。

旧推进代码还有一个适合读的工程问题。程序直接用固定下标取摇杆轴，而手动模式缺少针对摇杆消息停更的复位逻辑。读代码时可追“最后一次指令存在哪里”“哪个分支能把输出复位”。旧自动标志和心跳只描述程序状态，实际使用还要核对手柄连接和下游执行器行为。看旧启动入口时先阅读它会启动哪些节点。旧总 launch 包含电机相关动作，桌面软件验证使用单独的定位节点和模拟输入。

## 第 22 课 · 从 ROS 1 Noetic 迁移到 ROS 2 Humble

旧代码的工作空间是 `catkin_ws`，原板基线使用 Ubuntu 20.04 与 ROS 1 Noetic。新定位工作空间是 `orangpi_ros2`，目标是 Ubuntu 22.04 与 ROS 2 Humble。迁移时先为每个接口记录主题名、消息类型、单位、坐标系、频率和触发条件，再改调用方式。

| 关心的问题 | ROS 1 常见写法 | 这个 ROS 2 工程怎么做 |
| --- | --- | --- |
| C++ 客户端和节点 | `roscpp`、`ros::NodeHandle` | `rclcpp`、继承 `rclcpp::Node` |
| 消息类型 | `std_msgs::Float64` | `std_msgs::msg::Float64` |
| 创建端点 | `advertise`、`subscribe` | `create_publisher`、`create_subscription` |
| 调度回调 | `ros::spin()` 等 | `rclcpp::spin(node)`，可按需选择执行器 |
| 通信发现 | ROS master 提供注册与查询 | 使用 ROS 2 的分布式发现，端点还有 QoS 配置 |
| 参数 | 常用集中式参数服务器和私有参数 | 参数归属节点，通过节点接口访问，构造时声明和读取 |
| 构建与安装 | catkin | ament_cmake 与 colcon |
| 启动与配置 | 旧 `.launch` 的语法、参数与重映射 | 按 ROS 2 launch 语法重新组织，参数 YAML 按节点组织 |

新包已移植的是计算链路。缆绳 IMU 数据采集、缆长电机、推进执行、深度来源和飞控接入要分别确认供应方式。把每个输入当成一个接口，可以先在电脑给计算层喂已知消息，再在板上逐一替换为真实发布者，并比较字段和频率。旧系统仍在供数据时，ROS 1 与 ROS 2 需要兼容的桥接方案或逐段迁移，话题同名也不会自动互通。

移植时建议把每项观察放回三层。先确认操作系统能看到设备，再确认驱动能稳定发布符合约定的消息，最后看定位节点能否得出预期结果。例如发现空间坐标朝向不对，可以先把 IMU、标定输出和位姿分别观察一遍，判断错误从哪一层开始出现。

## 第 23 课 · 从现象定位到具体回调

### 现象一 · 节点存在，却没有位置输出

用 `ros2 node info /pose_node` 看实际的订阅和发布名称。随后查三路输入各自是否有发布者、是否匹配 QoS、是否收到有限数值。只看到缆长和角度时，回到 `publish_position` 的提前返回条件，深度缓存为空就能解释这个现象。节点名可被重命名，实际运行时先用 `ros2 node list` 找它。

### 现象二 · 有位置，但方向相反

先读消息的 `header.frame_id` 和三维坐标，确认观察工具使用哪个参考系。然后对照标定前与标定后的角度，检查正负、度与弧度、IMU 安装方向和 TF。比如标定后 +π/2 弧度在计算公式里应主要进入正 Y。若消息数值符合计算但画面方向相反，继续看观察工具选用的坐标参考和变换。

### 现象三 · 深度停了，位置还在发布

看深度和位姿各自的更新速率。定位节点持有最后一次深度，新的缆长或角度仍可触发解算。位置消息上的新时间戳代表程序重新算过，深度的采样年龄需要另外管理。可以从回调找出哪一路更新触发了位置变化，再考虑加入超时判断。

| 想观察的东西 | 读哪个接口 |
| --- | --- |
| 谁在运行，端点叫什么 | `ros2 node list`、`ros2 node info` |
| 两边都在，怎样确认类型和 QoS | `ros2 topic info -v` |
| 实际收到什么字段 | `ros2 topic echo` |
| 订阅者观测到的更新速率 | `ros2 topic hz` |
| 想重复观察一段输入 | 用 rosbag2 记录话题，再在隔离环境回放 |

录包时记下实际 launch 参数、消息来源和坐标约定。用于验证计算的回放，选定定位输入并留意回放时间与端点 QoS。这样能把“硬件数据偶尔异常”变成可以反复观察的一段输入。日志适合补充判断原因，例如某一路暂未收到或读数过期。可以控制重复日志的频率。

## 第 24 课 · 用测试判断改动是否真的有用

`test/test_localization.py` 是一个从安装后的 launch 入口启动节点的集成测试。源码用 C++，测试用 Python，因为协议隔在消息接口上。测试程序只要会发布和订阅相同类型，就能从外部观察行为。

1. **启动真正的入口。** `generate_test_description` 找到安装目录中的 XML，传 `with_ekf=true` 启动计算链路和可选融合。
2. **构造可控输入。** 测试创建发布器模拟缆长、深度和各路 IMU。开始时先让 `depth = None`，因此只发其他数据。等待循环定期发送和处理回调，让节点发现和接收有时间完成。
3. **同时观察中间过程与最终结果。** 回调用字典记住原始角、校准角、母船航向、调试点、位姿与融合里程计。单看最终里程计有时难以区分输入错误和滤波错误，查看中间话题能缩小范围。
4. **按约定断言。** 先验证没有深度时不发布位置，再加入深度验证位置、坐标系和协方差。测试从原始角开始走标定，期望值用展开的多项式计算。浮点用近似比较。测试也检查超深度时的水平归零、倾斜时的方位变化、母船 180° 安装偏置以及子船融合航向。

这些输入是软件构造的。测试能验证当前启动入口与计算链路，驱动、接线、时间同步和实船传感器量程需要在板上分别核对。

### 改进一 · 等真正收到母船航向再发布

现状是定时器会在第一帧前发布默认 0°。可让航向存为 `std::optional<double>`，有效姿态到达后才填值，定时器只在有值时发布。接收端要把启动阶段没有消息处理为“等待”，真实的 0° 仍可发布。验证时先让节点运行一段时间但不给 IMU，再提供一帧合法的姿态，观察发布由等待转换为正常更新。

### 改进二 · 给三路定位输入加新鲜度检查

当前三个缓存只有“有值”和“没值”。可以给每路缓存同时记录接收时刻。没有采样时间的 `Float64` 最先能做的是检查接收年龄。如果还要判断三路测量在同一时刻附近，需要上游提供真实采样时间，并核对时钟。阈值可以按每路实测更新频率选定，各路未必相同。测试可以先填齐三路，让其中一路停更但持续发另外两路，观察定位在超过阈值后等待新数据，再观察数据恢复。这样能保留正常情况下的定位行为，也能验证新增的超时分支。
