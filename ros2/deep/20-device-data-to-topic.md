# 一串设备字节怎样变成缆长话题

这一篇为第 21、22 课补上中间环节：为什么读了串口还需要解析、校验、换单位，如何用离线输入隔离硬件问题。示例使用自创文本协议和模拟测量。这套协议只是学习用，被备份的原电机驱动仍应按它自己的协议和设备说明阅读。

## 1. 从观察到一个数字，倒着问四层

在 `pose_node` 回调里看到 `msg.data == 5.0`。这个数字之所以成了 5 米，前面可能有：

1. 编码器记录机械旋转，设备根据协议给上位机发计数。
2. 系统串口读取到字节流。驱动看到了属于某条完整反馈的一组字节。
3. 驱动按协议解出计数，检查内容有效，应用零点、比例和方向得出实际距离。
4. ROS 2 发布者填入消息并发送，定位接收该数值并按米解释。

只有最后一步跨进程发送 ROS 消息。把串口对象、采样协议和 ROS 发布对象拆开理解，出现“话题不更新”时可先确定究竟缺原始字节、缺合法帧，还是最后发布名不对。

### 字节与整数是不同层面的数据

下列是教学协议的一行：`COUNT:5050`。假定物理设备用 ASCII 文本发送，以换行符结尾。ASCII 是 American Standard Code for Information Interchange（美国信息交换标准代码），每个字符对应一个字节值。串口驱动收到的是字符 `C`、`O` 等组成的字节流。字符 `'5'` 的编码值不是整数测量 5。解析器按十进制读取后才得到整数 5050。

如果设备协议用二进制整数，解析需遵守字段长度、字节顺序和校验。C 的经验可以在这里复用，但不能把字节数组直接强制转成随平台布局变化的结构体就认为可靠。要看协议是否允许错位、是否有长度、封包校验与重同步规则。示例用文本，是为了每个步骤都可以肉眼确认。

### 读串口一次给一帧吗

操作系统读接口通常返回当前可读的部分字节。假设设备顺次发送：

```text
COUNT:5050\nCOUNT:5051\n
```

一次读取可能只得到 `CO`，下次得到 `UNT:5050\nCOUNT:`，再下次拿到 `5051\n`。也可能一次收到两条。因此真实读取代码先把字节积累进缓冲，根据帧分隔或长度判断完整性。学过 C 时可把它理解为“解析函数只接受完整记录，串口读取函数负责把碎片拼完整”。

对本例的分行协议，可按换行分隔，遇到很长一行时有长度上限避免无限等待。真实设备最终应按手册处理截断、失步、超长和坏校验。解析器报告无效时，不应将无效记录当成测量 0。

## 2. 设计教学算例的接口合同

| 合同项 | 本例约定 | 为什么需要明确 |
| --- | --- | --- |
| 文本消息形状 | `COUNT:` 加十进制非负整数 | 有明确的前缀，便于区分消息类别 |
| 测量物理量 | 编码器计数 | 计数在解析层与米分开 |
| 零点 | 50 个计数 | 设备读 50 时真实长度为 0 |
| 换算比例 | 0.001 米/计数 | 5050 − 50 = 5000，得到 5 米 |
| 可接受范围 | 校准后计数非负，最大原始计数 100050 | 用于教学判断设备读数是否能用 |
| 对外话题 | 示例采用 `/study/length_m` | 命名和单位一并传给下游 |

设原始读数 5050。先减零点得到 5000，再乘比例 0.001，结果 5.0。设原始读数 50，则得到 0.0，仍是有效数据。设原始读数 49，属于低于零点，示例将它作为无效场景。真实设备若正负表示收放方向，约定要按机械结构定义。这里的范围只是讲解，让“合理读数与数学可计算”可以分开。

## 3. 一个可独立运行的 C++17 解码程序

下面模拟的是“驱动已经分出完整的一行文本”。每次处理一个字符串，可以把输出与上表量的变化对应。`std::from_chars` 接收字符区间，不会自动跳过空白。用返回的位置确保读完数字。

```cpp
#include <array>
#include <charconv>
#include <iomanip>
#include <iostream>
#include <optional>
#include <string_view>
#include <system_error>

std::optional<int> parse_count(std::string_view line) {
    constexpr std::string_view prefix{"COUNT:"};
    if (line.substr(0, prefix.size()) != prefix) {
        return std::nullopt;  // 这不是预期的测量记录。
    }

    line.remove_prefix(prefix.size());  // 视图移到数字开头，无需复制字符串。
    if (line.empty()) {
        return std::nullopt;
    }

    const char* first = line.data();
    const char* end = first + line.size();
    int count{};
    const auto parsed = std::from_chars(first, end, count);
    if (parsed.ec != std::errc{} || parsed.ptr != end) {
        // 包括无数字、超出 int 可表达范围、或数字后有残留字符。
        return std::nullopt;
    }
    return count;
}

std::optional<double> to_meters(int raw_count) {
    constexpr int zero_count = 50;
    constexpr int maximum_count = 100050;
    constexpr double meters_per_count = 0.001;

    // 先验证范围，再减零点与乘比例。
    if (raw_count < zero_count || raw_count > maximum_count) {
        return std::nullopt;
    }
    return (raw_count - zero_count) * meters_per_count;
}

int main() {
    const std::array<std::string_view, 7> samples{
        "COUNT:5050",             // 正常读数，5.0 m。
        "COUNT:50",               // 合法零值。
        "COUNT:49",               // 可解析的整数，物理范围不接受。
        "COUNT:5050junk",         // 读到整数，但还有尾字符。
        "STATUS:5050",            // 不是本例测量类型。
        "COUNT:",                 // 缺数字。
        "COUNT:999999999999999",  // 整数溢出。
    };

    for (const auto line : samples) {
        std::cout << line << " -> ";
        const auto raw = parse_count(line);
        if (!raw) {
            std::cout << "malformed measurement\n";
            continue;            // 跳到下一次循环，继续处理下一条。
        }

        const auto length = to_meters(*raw);
        if (!length) {
            std::cout << "outside calibrated range\n";
            continue;
        }

        std::cout << std::fixed << std::setprecision(3) << *length << " m\n";
    }
    return 0;
}
```

`std::string_view` 是对一段已有字符的只读视图。它保存可访问范围，不拥有或复制文本。示例数据来自在程序里一直存在的字符串字面量，足以支撑视图。真实驱动如果把视图保存到回调以外，必须确认对应缓冲不会先释放或重新分配。需要独立拥有一份文本时，用 `std::string`。

`end` 指向区间结束后，和 C 的指针区间用法类似。`from_chars` 返回两个信息，`ec` 表示解析结果状态，`ptr` 表示停在哪里。输入 `5050junk` 时，转换可能成功读出 5050，但停在 `j`。条件要求位置正好到末尾，所以这条帧被拒绝。第一个函数解决“文本能否按约定解释为一个整数”，第二个函数解决“这个整数能否按标定换成可用的距离”。各自返回可选值；它们保护不同的边界。

`continue` 只结束本次循环，程序仍处理下一条。它和回调里的提前 `return` 类似，都是在判断条件不能继续时尽早结束当前处理单元。合法零由 `optional` 单独保存，不会被误看成失败。

## 4. 如何把解码结果交给 ROS 而不让两层纠缠

ROS 封装应在完整且有效的读数出现后创建消息。用以下局部片段把独立函数接回 ROS 2。它位于驱动处理完整行的位置，`publisher_` 由节点持有。

```cpp
const auto count = parse_count(frame);
if (!count) {
    return; // 本帧无法解析，由驱动计数或记录诊断。
}
const auto length = to_meters(*count);
if (!length) {
    return; // 本帧超过已知的标定范围。
}

std_msgs::msg::Float64 sample;
sample.data = *length;
publisher_->publish(sample);
```

这是“设备输入到应用接口”的桥。若没有完整有效的结果，不创建一条默认的 0.0 消息。避免让下游把“错误”当成“缆绳为零”。如果上层需要知道错误种类，可以附带诊断，例如分别统计帧格式错误和超过范围。单一数值话题无法解释错误原因。

等待串口数据可以阻塞线程。定位和控制若也在同一单线程执行器，阻塞会延后其他回调。通常把硬件读流程做成独立节点或有明确的异步接收设计，计算节点只消费已解码的消息。采集能在没有定位系统时独立验证，是拆分层的实际好处。

## 5. 对照原板的旧驱动，怎样做迁移笔记

阅读 `usv/src/motor.cpp` 可以在纸上画一列“供应读数”，一列“接收控制”。先找打开设备还需要的通信参数、错误处理和实际报文。再找读到的数据如何转换成缆长。最后找创建的 ROS 发布器和命名。写下以下信息，比只记一个串口名更利于复现：

- 设备如何识别，旧程序实际打开哪个别名，板端权限从哪里来。
- 旧驱动用什么协议字段读反馈，哪个数用于长度换算。
- 对应的零点、符号、比例在哪里配置，是否和机械绕线方向相关。
- 串口失败时返回什么，驱动是否在重连。
- 话题上打算保留的名字、类型、单位、更新频率和时间约定。
- 采集链能不能在未连接推进控制的情况下独立验证。

当前课程的具体文本内容是自创演示，旧驱动应在原文件核对。不能把 `COUNT:` 或示例换算参数用来控制或解释原船设备。

## 6. 从一个“话题突然没更新”推到可观测原因

假设先在旧系统录到几条已知反馈，接着迁移：

| 看到的证据 | 优先判断 | 下一步 |
| --- | --- | --- |
| 系统没出现预期设备或别名 | 设备连接、规则或驱动环境未就绪 | 板端核对设备识别与权限 |
| 能打开串口，但字节计数始终为零 | 设备没送、接线或参数不匹配 | 核对上电、串口设置、数据的方向 |
| 有持续字节，没有有效帧 | 分帧或校验环节与设备协议不一致 | 对照已知可用样本，区分碎片和坏帧 |
| 有有效帧，整数变化和预期相反 | 解释或零点符号不一致 | 对比编码器运动、方向和比例 |
| 缆长值正确，定位端没收到 | ROS 接线或策略不匹配 | 看话题名称、类型、QoS 与实际端点 |
| 定位端已收到，仍无位置 | 还缺另一路或值验证不通过 | 回到方位、深度和三路缓存 |

先保存观测的物理单位与原始输入，再追下游数。这样即便设备无法随时接到电脑，也能使用先前保存的字节或消息做离线判断。把错误捕获在最早能解释证据的层，比一开始修改三角公式更直接。
