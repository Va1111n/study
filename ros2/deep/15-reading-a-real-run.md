# 一次定位运行从启动日志追到最终输出

这一篇给你一份完整的带讲解阅读记录。它用的是合成数据和示意输出，话题名、消息字段和业务分支对照现有工程。阅读时不需要运行命令。目标是形成因果链，看到某一行返回值时能判断它证实了什么、还要到哪一步取证。

## 1. 我只想验证位置公式，应该启动什么

观察目标是“5 米、0 弧度、3 米是否变成 `(4, 0, -3)`”。只启动 `usv_localization` 的 `pose_node` 就够。角度从**标定后**入口人工给定，绕开姿态、滤波和标定。位置正确时，能说明计算程序按约定吃进去三路值，不能说明缆绳 IMU 或实船深度已接通。给这个结论定清测试边界，就知道下一步应从哪个入口往前延伸。

对于实际观察，订阅和发布进程在同一个本机通信环境。把程序跑起来以后，先看节点图。这里假设还没有开模拟输入，节点端点可能呈现以下简化结果：

```text
/pose_node
  Subscribers:
    /sensor/cable_azimuth: std_msgs/msg/Float64
    /sensor/cable_length: std_msgs/msg/Float64
    /sensor/relative_depth: std_msgs/msg/Float64
  Publishers:
    /solver/debug_point: geometry_msgs/msg/PointStamped
    /solver/pose: geometry_msgs/msg/PoseWithCovarianceStamped
```

实际工具还会列出额外的参数、日志等系统端点。这里提取用于理解定位的部分。这份图证明构造函数已经做完这些注册。看不到订阅器时，要回到启动配置和节点名。看得到发布器不能推出它执行过 `publish`，接下来才看输入。

## 2. 一条缆长消息，从工具输出读到内存

模拟上游往目标话题发 `data: 5.0`，我们的首个观察应看到相应话题存在发布者。带详细信息的输出可以概括为：

```text
Topic: /sensor/cable_length
Type: std_msgs/msg/Float64
Publisher: synthetic_input, Reliability RELIABLE
Subscription: pose_node, Reliability BEST_EFFORT
Message received by a compatible observer:
  data: 5.0
```

同一个类型加可匹配的 QoS，说明有条件连接。看到兼容观察者读到 5.0，说明生产端发了数据。要确认真正进了定位回调，可以在代码的有效值检查和缓存更新处记录经过的事件，或结合后续输出判断。这是多个可观测点。分开观测能区分“生产端发了”和“业务回调确实处理过”。

假设缆长回调已处理，内存大致如下：

```text
current PoseNode:
  length_ -> present, 5.0
  angle_  -> absent
  depth_  -> absent
```

`publish_position` 立即返回。执行器重新等待，定位话题暂时无消息。若运行时只看到这一步，系统正常地等另外两路。此时定位 `echo` 窗口安静，不能仅凭安静确定故障。

## 3. 错把角度发到标定前的话题会怎样

我们只启动了 `pose_node`。如果模拟源往 `/sensor/cable_azimuth_original` 发了零，图上会多一个原始角发布端。定位订阅的是 `/sensor/cable_azimuth`，原始角与标定角之间需要 `cable_angle_calibrator`。没启动它时，两边各自都能列在图里，但名字不同。

```text
/sensor/cable_azimuth_original
  发布端：synthetic_input
  定位节点并未订阅此名称

/sensor/cable_azimuth
  订阅端：pose_node
  需要模拟发布或真实标定后的输出
```

典型误判是“我已经给了角度，公式不工作”。正确的判断是“我给了当前节点不订阅的入口”。这一步先处理接线：只验证公式就直接向标定后入口发送；想验证标定过程，就额外启动标定器，给原始角，并改用相应数值作参考。这样不必修改定位源码。

## 4. 三路到齐后把输出读成一棵树

第三条消息使用深度 3.0，前两路实际缓存为 5.0 和 0.0，才应得到示意结果：

```yaml
header:
  stamp:
    sec: 123
    nanosec: 456000000
  frame_id: mother/base_link
pose:
  pose:
    position:
      x: 4.0
      y: 0.0
      z: -3.0
    orientation:
      x: 0.0
      y: 0.0
      z: 0.0
      w: 1.0
  covariance: [ ... ]
```

这里的时间数字只用于解释字段。`header` 的缩进告诉你它属于整个消息，`position` 位于两层 `pose` 下。C++ 访问 `out.pose.pose.position.x` 与命令输出的层次一致。ROS 的时间戳把整数秒和纳秒余数分开，这组示范约为 123.456 秒。它标的是解算时刻。朝向的单位四元数是占位，XYZ 才由这条链测得。

同步观察 `/solver/debug_point`，字段变成 `point.x`、`point.y`、`point.z`。原程序复用位姿的头部和位置。若两个观察工具分别打印了一帧，它们可能来自不同的计算事件。要比较“同一次”的输出，先按消息里的时间戳选对应的帧，再比较数值。

## 5. 现在加上原始方位到标定的链

这次从原始角给零。流程变成：

```text
synthetic_sensor: /sensor/cable_azimuth_original = 0.0
  ↓
cable_angle_calibrator 收到、减零偏、代入多项式、规约
  ↓
/sensor/cable_azimuth ≈ -0.024 rad
  ↓
pose_node 收到标定角，与缆长 5、深度 3 结合
  ↓
/solver/pose: x ≈ 3.999，y ≈ -0.097，z = -3
```

对比上一轮，多出一段独立计算，结果的 Y 因此略有偏移。看到偏移的问题不再是“为什么不符合我的直角三角形”，而是“我从哪个点注入，输入到三角形的角到底是多少”。在现场记录中写明观测入口，并同时看原始角和标定角。如果原始角缺失，从 IMU 向前查；若标定输出缺失，从标定器订阅和有效值条件查；若角已对，才查三路定位。

这里正在验证从原始角到位置，缆绳 IMU 给不出四元数的情形还没有覆盖。把模拟入口往前移到 `/imu`，可选择 `(0,0,0,1)` 的竖直状态和绕 X 转 0.5 弧度的倾斜状态。观察原始方向是否随倾角改变，再看标定后的对应结果。这样验证是逐段加进来的，每次失败也能知道新增了什么依赖。

## 6. 用一次消息消失判断应该往哪边查

我看到“母船航向正常，但定位输出不变”。这个现象可以有很多解释。航向正常说明母船姿态输入链路有工作迹象；定位直接消费的是缆长、标定后角和深度。母船航向即使持续 50 Hz，也不能给缺深度的计算补齐信息。

给定下面的合成观测，按因果找第一个异常点：

| 观察处 | 合成观察 | 能怎么解释 |
| --- | --- | --- |
| 航向 `/mother_usv/imu/yaw` | 270° 快速重复 | 定时器有工作，值可能是近期或缓存的母船姿态 |
| 缆长 `/sensor/cable_length` | 由 5.0 到 5.1 | 至少模拟缆长端在更新 |
| 标定角 `/sensor/cable_azimuth` | 时间上持续有新样本 | 缆绳方向链已能提供下游输入 |
| 深度 `/sensor/relative_depth` | 启动时有一次 3.0，之后观察不再变化 | 要分清内容不变与消息停更，必要时看接收频率 |
| `/solver/pose` | 时间戳继续变化 | 定位重复解算，不能推出深度在更新 |

如果深度内容不变而重复发送，说明通信持续但环境或上游计算可能稳定；如果已不再有消息，定位仍使用旧缓存。这两个外部现象在单看位姿数值时很像。时间、端点和频率是不同的证据。解决方式对应不同根因：驱动失联要修采集，数据标记或新鲜度要修接口，状态本身稳定无需修改算法。

## 7. 一段“跨设备失败”的具体读法

假设电脑用模拟数据工作正常。把输入发布端搬到香橙派，同一台机器内部观察仍有值，但 WSL 的监听不再看到它。这个场景先查发现和通信，不先改 `PoseNode` 的几何代码。

1. 对照两端是否都运行相同的 ROS 2 目标环境。这决定接口版本和工具行为。
2. 查看双方实际话题名、类型、域标识以及是否有本机限定。发现失败时，先解释域和网段再看上层。
3. 确定发布端在板上能被同机订阅。如果同机也收不到，回到本机驱动和 QoS。
4. 若两端互相列出端点，核对兼容策略并观察是否真正接到消息。网络发现与数据交付两个环节都要验证。
5. 收到以后检查实际单位和帧。这些条件仍可能与电脑模拟输入不同。

手机热点、WSL 模式、无线客户端隔离和中间件设置都可能影响发现。只有现场观察到网络行为后才能定位原因。若只是给软件计算做测试，继续留在隔离的本机环境可以减少额外变量。保持开发验证和实船集成观测各自的目的即可。

## 8. 最后验证滤波链，不用一开始就怀疑 EKF

先确认直接位姿通过，再开启 `with_ekf`，看子船的姿态与静态变换。在一个合成场景里，子船 IMU 四元数绕 Z 取非零值，位置仍来自缆绳估计。最终输出含接近预期的位置，也有子船的非零姿态。只要其中一项不对，就能沿 YAML 里两个输入分别回查。若位置正确、只有方向为单位四元数，先查子船 IMU 是否有效和配置是否选姿态，而不应把母船航向话题当成子船输入来替代。

观察消息头识别用途：`header.frame_id` 标明结果参考系，`child_frame_id` 标记子船本体。话题在 `/rov` 命名空间，与 frame 命名是不同层面的选择。改话题名不会自动修复 TF 链。

## 9. 一条清楚的实验记录长什么样

可以用这个阅读范例对照自己的观察：

```text
目标：只检验 pose_node 在三路各到一条时的几何输出。
启动：单独的计算程序，在本机通信域内。
注入点：缆长话题、标定后角度话题、相对深度话题。
输入：5.0 m，0.0 rad，3.0 m。
观测：前两路已收到，没有位置；第三路后收到 (4,0,-3)，
     参考系为 mother/base_link，调试点与同次位姿一致。
结论：本次输入合同与期望位置计算吻合。
需另测：板上实际测量的单位与采样时刻、深度发布端、TF 安装关系。
```

它有明确的输入、可观察事件和输出，且能追到哪一段代码采用了哪个条件。读懂整个工程，就是能对别的症状写出同样可重现的因果链。
