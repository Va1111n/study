# 一个话题怎样连接两个 ROS 2 程序

本篇对应第 12～15 课。要建立的图是：一个进程计算一个数，创建一条消息，把它交给发布器；另一个进程通过订阅器获得接收机会；执行器最后调用你写的函数。船上接收缆长和发出位置走的也是这组步骤。

## 第 12 课 · 节点、进程、端点、话题和消息

假设要把 5 米送给定位节点。先决定通信契约：

| 问题 | 约定 | 为什么要写清楚 |
| --- | --- | --- |
| 谁负责提供测量 | 缆长驱动或模拟发布端 | 定位节点依赖输入，驱动不运行就无此读数 |
| 数据流叫什么 | `/sensor/cable_length` | 双方按可解析名称匹配 |
| 一条消息是什么类型 | `std_msgs/msg/Float64` | ROS 需要同一种字段定义 |
| 看哪个字段 | `data` | 此类型只包含一个数 |
| 数值 5.0 的单位 | 米 | 同为浮点类型仍能表示厘米、温度或角度，应用必须约定语义 |
| 发多快 | 由设备和驱动配置决定 | 影响接收速率、队列和过期判断 |

ROS 表示 Robot Operating System（机器人操作系统）。ROS 2 为机器人程序组织通信、配置和运行提供接口。节点是通信图中的参与者。运行一个可执行文件，会创建一个操作系统进程；在本项目中四个可执行文件各创建一个节点。其他设计可以在同一进程运行多个节点。功能包是构建和安装组织单位，当前一个包提供四个可执行文件。你看到 `ros2 run usv_localization pose_node` 时，依次是工具、启动操作、包名、可执行文件名。启动后节点名默认也叫 `pose_node`，是构造函数里明确给出的名字。二者恰好同名，改变其中一个可以完全不改变另一个。

从 C 的视角看，普通函数调用的参数存在同一个进程里。话题让两个独立程序交换消息。一个发布者可以服务多个订阅者，一个订阅者也可能收到同话题多个发布者的消息。关键数据通常只设一个正式来源。诊断中若同时启动模拟发布端和真设备，看到两个值来回跳，先检查是否有多个发布者。

### Float64 这一串名字怎么读

终端显示 `std_msgs/msg/Float64`。`std_msgs` 是 Standard Messages（标准消息包），`msg` 是 Message（消息），`Float64` 是 64 位浮点消息。C++ 中写 `std_msgs::msg::Float64`，对应头文件是 `<std_msgs/msg/float64.hpp>`。终端的斜线、C++ 命名空间的双冒号和头文件路径各有用途，都指向这份消息接口。

C++ 中写 `Scalar sample;` 是创建一个消息对象，`sample.data = 5.0;` 把值填入字段。`Scalar` 是用 `using` 起的别名。消息可以理解成由接口定义生成的数据结构。ROS 2 有能力把它从一个进程中的内存表示转换成可传输形式，再在接收端恢复字段。直接把一个进程里的地址发给另一个进程没有这样的含义，因为地址只在原进程的地址空间里有效。

### 服务和动作在什么场景才出现

话题适合一串持续到来的状态或测量。服务有明确的请求和响应，适合查询或快速处理一次操作。动作（Action）适合一项会持续一段时间的工作，可以返回进度、结果，也可以请求取消。需要每秒连续更新的缆长不必为每帧发请求。将来若设计“查询当前标定参数”，可以考虑服务；若设计一项需要进度与取消的长任务，可以考虑动作。从这个项目的订阅构造函数就能确认定位主链选择的是话题。

## 第 13 课 · 从发布器、订阅器读到可执行程序

船的 `pose_node` 收三路发两路。为了先学通用写法，我们取独立的教学话题 `/study/length_cm` 与 `/study/length_m`。一端发厘米，一端收到以后换算成米，再发布。原教程有可独立编译的转换节点。[完整转换节点](../03-ros2-communication.md#第-13-课--写一个最小的订阅和发布节点)

### 发送端把一次计算拆成哪些动作

下面是可与转换节点配合的教学发送程序。固定频率发布样例，避免观察者稍迟启动只错过唯一一帧。它在 `/study/` 名下工作。

```cpp
#include <chrono>
#include <memory>

#include <rclcpp/rclcpp.hpp>
#include <std_msgs/msg/float64.hpp>

using Reading = std_msgs::msg::Float64;

class DemoSource : public rclcpp::Node {
public:
    DemoSource() : Node("length_source") {
        // 先建立端点，再登记可能用到它的定时回调。
        length_cm_pub_ = create_publisher<Reading>("/study/length_cm", 10);
        timer_ = create_wall_timer(std::chrono::milliseconds{500}, [this] {
            Reading sample;      // 每次定时事件创建一条新的消息。
            sample.data = 500.0; // 本话题约定输入单位为厘米。
            length_cm_pub_->publish(sample);
        });
    }

private:
    rclcpp::Publisher<Reading>::SharedPtr length_cm_pub_;
    rclcpp::TimerBase::SharedPtr timer_;
};

int main(int argc, char** argv) {
    rclcpp::init(argc, argv);
    rclcpp::spin(std::make_shared<DemoSource>());
    rclcpp::shutdown();
    return 0;
}
```

把发送程序当作“拥有一支定时写入数据流的端点”。`create_publisher<Reading>` 指定将来发送的消息种类。话题名是第一个函数实参。历史深度 `10` 是端点的配置，影响保留消息的范围，和定时频率没有换算关系。`timer_` 保存了定时器的持有者，就像 `length_cm_pub_` 保存了发布器持有者。若只写在局部变量里而且没有其他持有者，构造结束后定时器就会析构。

定时回调中，每次事件先得到一个新的局部变量。它的作用域就是回调体这一对大括号。`publish(sample)` 返回后这段回调可以正常结束。其它进程在稍后通过自己的订阅接口收到消息。消息创建时间、调用发布接口的时间和订阅回调运行时间是三个不同的观测点。

### 接收端怎样知道该调哪个函数

转换节点的订阅器表达了三个请求：

1. “我关心 `/study/length_cm`。”
2. “每条消息用 `Scalar` 表达，端点按传入的通信配置工作。”
3. “收到一条可处理消息时，把它交给这个 lambda。”

在 `[this](const Scalar& input)` 中，`input` 是这次收到的消息，引用让这次回调直接读取传入对象。`this` 让回调找到保存于同一节点的米值发布器。若你把 `input.data` 直接赋给输出对象，数值 500 将原样得到保留。`output.data = input.data / 100.0;` 这一步才把单位从厘米换成米。换完单位记得发到约定为米的话题，让下游按 5.0 米解读。

可以在一处回调中消费输入、更新状态和发布输出。本工程的标定器就是这样的节点。定位节点回调也会发布，但它还有跨消息保存状态和等待三路到齐的环节。先读通一路转换，就知道定位程序的复杂度增加在哪里。

### 各事件之间不必紧挨着发生

```text
发送进程                             接收进程
构造发布器与定时器                    构造订阅器与米值发布器
spin 等事件                          spin 等事件
定时器到期
创建 data=500.0 的厘米消息
publish ─────── 中间件交付 ──────→   订阅回调可被调度
                                     取 input.data
                                     除以 100.0
                                     发布米值
回到等待                             回到等待
```

两个进程独立启动，发现与匹配需要时间。采用默认易失策略时，尚未匹配上的订阅端可能看不到之前发布的数据。持续发一个固定样例，可以让它在匹配后再收到一帧。这个原因也解释了为什么测试通常等通信建立、持续喂输入并按条件等待输出。

### 同类题目在船上怎么找

| 在示例里 | 在船上 | 应该一起核对的部位 |
| --- | --- | --- |
| `/study/length_cm` | `/sensor/cable_length` | 单位必须问上游，名字相似只说明用途 |
| `LengthConverterNode` | `PoseNode` | 构造函数设置端点，计算发生在事件到来后 |
| 输出 `Scalar` | 输出带坐标与时间的 `Pose` | 消息字段由接口约定，哪一层写坐标要看布局 |
| 一条输入即可换算 | 要有三路输入才会解算 | 查所有订阅和缓存门禁 |
| `length_cm_pub_` | `pose_pub_` | 成员持有端点，执行 `publish` 才发一条消息 |

## 第 14 课 · 谁轮到回调去执行

`spin` 把节点加入执行环境，等到订阅可读、定时器到期等事件。执行器（executor）负责选择可以执行的回调并调用它。想象 `main` 一直堵在 `spin`，只有停止程序时才走到下面的 `shutdown`。这解释了摆在 `spin` 下一行的普通打印为什么启动时迟迟看不到。

船代码中常规的 `rclcpp::spin(node)` 走单线程执行器。假设某个回调正在处理角度，另一路缆长这时就绪，缆长回调不能抢进来修改同一个应用层缓存，要等当前回调让出线程。就绪顺序、接收队列和调度都会影响什么时候处理。不要从文件里订阅器声明的顺序推断实际处理顺序。调试时能确定“一次回调内先写缓存后计算”，到达先后要从观察证据确认。

母船航向节点用了两个回调。收到 IMU 数据时更新 `heading_`；定时器到期时发布 `heading_`。20 毫秒是 0.02 秒，倒数为 50 Hz（Hertz，赫兹，每秒次数）。如果 IMU 每秒十次，定时器在新值到来前可多次重发同一测量。这是应用逻辑。定位节点采用另一种方式，三值到齐后，每次有新输入才尝试算。实际频率受输入速率、执行器和回调耗时影响。

高耗时操作会占住单线程回调。以后若把串口等待直接放进计算节点的回调，可能让角度输入无法及时处理。常见设计是采集放单独节点，定位节点尽量短时完成计算。改成多线程执行器时，需要知道哪些回调组允许并发，以及缓存读写需要怎样保护。共享智能指针能管理对象寿命，不能代替同步机制。

## 第 15 课 · QoS 为何决定“话题看得到，数据却收不到”

QoS 是 Quality of Service（服务质量）。可以先把它理解为端点对交付方式的约定。话题名和类型相同后，还要判断发布端提供的能力能否满足订阅端请求。

- **可靠性**关心是否需要按可靠交付策略处理。Reliable 发布端可以匹配 Best Effort 订阅端。Best Effort 发布端无法满足 Reliable 订阅端对可靠性的要求。
- **历史**关心保留哪些样本。`keep_last(10)` 表示在此端点按配置保存最近十条历史。新读数很快到来而处理跟不上时，较早读数可能不会都到业务回调。深度 10 不代表保留十秒。
- **持久性**关系到后接入的订阅端是否能获得保留样本。船的普通传感器消息通常是 Volatile（易失）。数据就绪以后的观察者从新样本看起。静态坐标变换有自己的发布方式，适合支持晚加入者取得固定信息。

以下几种情况外观看起来都是“没有收到”，追法不同。

| 看到什么 | 应先问的问题 | 获得证据的位置 |
| --- | --- | --- |
| 找不到目标话题 | 进程正常启动了吗，还是写错了命名空间 | `ros2 node list` 和启动输出 |
| 只看到一个订阅端 | 谁提供数据，发布端名字是否一致 | `ros2 node info`、`ros2 topic info -v` |
| 两边均能列出 | 类型和 QoS 能匹配吗 | `topic info -v` 的类型及可靠性等字段 |
| 同一设备能收到，跨设备收不到 | ROS 域和网络发现设置一致吗 | 两端环境变量、网络和中间件发现 |
| 能看到输入，定位输出缺失 | 解析之后哪个条件提前返回 | 三路读数是否有效、缓存是否到齐、日志与源码 |
| 偶尔有响应 | 是发布变慢、接收队列被挤掉，还是回调处理不过来 | 同时记录发布频率、接收频率、回调耗时和时间戳 |

`SensorDataQoS` 是 ROS 2 的传感器数据预设。在定位包的输入端，代码用它再设置历史深度。当前选择 Best Effort 可与常见传感器发布者连接。输出端使用普通默认端点配置，可靠性通常为 Reliable。`ros2 topic echo` 是一个新订阅者，调试时它本身也要选择能匹配的策略。

DDS 是 Data Distribution Service（数据分发服务）。ROS 2 Humble 常通过 DDS 中间件发现其他端点。`ROS_DOMAIN_ID` 是通信域标识，同一应用节点通常放在同一域。`ROS_LOCALHOST_ONLY=1` 让一组本机演示留在本机。电脑和香橙派联合运行时，要确保配置允许跨设备通信，再检查各自使用的域和话题。只凭两台机器都登录了 ROS 环境，无法推断通信已经接通。
