# 从报错提示反推是哪一层出了问题

本篇给出第 09～11、15、16、23 课的常见错误实例。所有提示是便于阅读的示意，真实文本会随工具、环境和版本变化。目标不是背报错，而是从第一个错误开始问“谁报的，输入读到哪，哪个后续动作还没发生”。

## 1. 写完 .cpp，编译器在读语法

### 现象 · 编译器说 cout、setw 或 setprecision 找不到

```text
error: 'cout' is not a member of 'std'
error: 'setprecision' is not a member of 'std'
```

先看源文件是否包含对应声明。`<iostream>` 声明输出流，`<iomanip>` 声明 `setprecision`。命名空间写对，但声明未出现在当前翻译单元，仍然不认识名字。反过来，已经包含头文件却只写 `cout`，可明确用 `std::cout`。调试先修第一处真报错，后面的许多错误可能由前面语法没解析成功引出来。

若从 C 编译器模式构建 C++ 文件，也会看到很多 C++ 语法和标准库不可识别。先核对文件扩展名、编译目标是不是用 C++、标准级别。不要逐个删掉构造函数和命名空间试图让它像 C。`std::optional` 需要 C++17 与 `<optional>`。船包从 CMake 给目标声明 C++17 要求，普通示例用独立 C++ 编译器也要指定合适标准。

### 现象 · 编译器说某个数不是类对象

下面两个写法有意放在一起对照：

```cpp
Scalar message;          // 一条对象，字段用点号。
message.data = 5.0;

auto publisher = create_publisher<Scalar>("/study/measurement", 10);
// 这里 publisher 是智能指针，箭头才进入发布器对象。
publisher->publish(message);
```

若写成 `message->data`，编译器会报类似“箭头操作数类型错误”。若写 `publisher.publish`，会试图在指针包装类型上找成员。看变量声明，或者回到右端的返回类型推断对象或指针。`auto` 只省略写类型，实际类型仍由初始化表达式确定。可用编辑器查看推导类型，也可以从接口文档确认。`const Scalar&` 在课内的多数回调里是消息的引用，访问字段仍用点号。

### 现象 · ROS 1 的消息名字在 ROS 2 找不到

示意错误：

```text
fatal error: std_msgs/Float64.h: No such file or directory
```

先核对当前代码和目标系统。ROS 2 C++ 头常用 `<std_msgs/msg/float64.hpp>`，类型写 `std_msgs::msg::Float64`。旧代码 `std_msgs::Float64` 属于旧接口习惯。头文件改对后，还要检查包清单和 CMake 是否声明目标依赖。如果在普通终端单独调用 `g++ 文件.cpp`，还缺 ROS 2 头文件与链接设置。以 ROS 2 功能包方式构建能把这些工作配置清楚。

### 现象 · 编译器接受了，程序表现还是奇怪

C++ 编译负责确认语法、类型和允许的行为。把米当厘米、用旧时刻的读数、选择错误的帧，类型仍合法。下面这个写法也能编译：

```cpp
auto covariance_copy = message.pose.covariance;
covariance_copy[0] = 0.1;
```

这里改的是副本。若需求是写入待发布消息，必须保留引用。观察局部数值和线上消息字段，定位是不是修改到了目标。与其只看“没有红字”，不如给一条你能预测的输入，检查有因果关系的输出字段。

## 2. 代码读懂了，链接器为什么还说找不到函数

从[构建详解里的三文件例子](05-workspace-inside.md)继续。`meters.hpp` 写了声明，`main.cpp` 使用它，`meters.cpp` 定义它。如果目标包含 `main.cpp` 却漏了 `meters.cpp`，可能在最后报：

```text
undefined reference to 'centimeters_to_meters(double)'
```

编译器已经知道签名，因此能生成“调用此函数”的目标代码。链接器要找到它的真正实现。先核对 CMake 的这个目标有无实现源码或链接库，再核对声明与定义的参数、命名空间和限定符。同名但参数不同是两个不同函数。若一个目标中塞入两个各带 `main` 的源文件，则会出现重复定义入口。每个可执行文件要单独定义构建目标。

船的 `CMakeLists.txt` 通过循环为四个节点分开配置。`pose_node` 处理几何消息，`imu_test1` 和母船节点共用头里的姿态检查函数。遇到链接问题时，从具体失败的目标反查源文件与依赖，比给所有目标一股脑添加所有包更容易复核。

## 3. 构建成功，为何命令找不到包或启动文件

### 能找到 ros2 工具，查不到自建包

可以把环境想成多层查找地址。加载 Humble 后，基础工具和平台包可见。构建自己的工作空间时，可执行程序还要安装，并将这个安装环境加载到当前终端。看到 `Package 'usv_localization' not found`，通常先追三个点：

1. 这次构建说目标包成功了吗？构建的源码目录真的是船的 `orangpi_ros2` 吗？
2. 输出是在常规 `install/`，还是命令指定的另一处？
3. 当前终端加载的是哪一份 `install/setup.bash`？它是否为刚构建的工作空间？

WSL 的两个终端可以有不同环境。一个运行系统 ROS 2，另一个加载了另一份覆盖工作空间。源文件同名无法证明运行的是同一版本。可用包前缀查询实际来源，再看预期产物的修改时间和进程重启记录。对比安装区真实文件比到处重复安装依赖更快。

### 能找到包，但找不到 exec 或 launch

若 `ros2 run` 已识别包名，下一层是执行目标有没有被安装到包的可执行目录、名字是否一致。若 `ros2 launch` 报找不到 XML，核对 CMake 是否把 launch 安装到共享区。若 XML 存在但进程没起，继续读它用的包名、目标名和运行依赖。错误的三个层次如下：

| 能找到的最后一步 | 仍然缺什么 | 第一处要查 |
| --- | --- | --- |
| 只有 `ros2` | 自建包索引 | `colcon` 结果、安装环境 |
| 找得到包 | 目标可执行文件 | `install(TARGETS ...)` 与目标名 |
| 找得到包和 XML | 被启动的程序或外部配置 | XML 的 `pkg`、`exec` 和配置文件安装 |
| 进程启动即退出 | 参数与运行依赖，或业务初始化报错 | 进程自己的日志、返回状态 |
| 相邻程序都能运行 | 端点与数据 | 图、话题类型、QoS、有效值 |

### 文本改了，结果还像旧版本

假设你在 Windows 编辑了 `pose_node.cpp`，在 WSL 运行。程序继续给相同结果，先验证 WSL 构建中用的是同一源文件，构建和安装更新到正确目录，原进程已退出，然后新进程从更新目录启动。对 launch 修改也是类似，若安装时是复制文件，改源码未安装就可能仍用旧入口。若使用符号链接安装，仍要确认程序类型和该文件的部署方式，C++ 编译产物依然需要重编。

## 4. 进程都活着，拿图继续缩小问题

### 只有一个话题名，无人发布

ROS 图显示有 `/sensor/relative_depth`，但详情只有定位订阅者。能验证订阅注册；要追实际深度来源。启动纯 ROS 2 计算包默认不会生成这条物理测量。搭建教学运行时用合成输入；部署时按旧设备接口和运行系统确定发布源。

### 两个相似名字，原来一个有前缀

标定器在 `/mother` 下发布一个相对名，解析成 `/mother/sensor/cable_azimuth`。定位以绝对名订阅 `/sensor/cable_azimuth`。看字符尾巴相同，完整名字不匹配。把两个节点的详细端点都列出来就有直接证据。改名、launch remap 或重新组织命名空间三种方式都可以建立合同，选一种并同时核对发布端和订阅端。

### 两个端点在图上同名但没有流动

先核对消息类型。再看 `ros2 topic info -v` 公布了什么 QoS。若发布 Best Effort，而订阅请求 Reliable，端点即使被发现也不能按这项要求正常匹配。转换成可兼容设置之后，确认这符合系统交付要求。若应用必须用可靠性，不应只是为了看到输出就将所有端点换成尽力交付。还要确认双方真的在发布与处理新帧；QoS 匹配只说明交付条件成立。

## 5. 从工作现象倒过来验证修复

假设观察“位姿没有输出”，后来发现角度话题命名空间不同。一次完整修复验证要走三个点：

1. 修改部署配置后检查两个端点显示同一最终名字。说明接线已变。
2. 给已知原始角或标定角，核对消费者读到正确的单位与数值。说明消息实际走到下游。
3. 同时提供已知缆长与深度，用位姿坐标确认业务结果。说明接线修复后算出的语义符合预期。

只通过第一点容易忽略类型或 QoS，只有第三点又可能有隐藏的模拟发布者顶上，不能确定真实设备环节已接好。逐层记录证据有助于以后复现。不同层的错误，提示的位置和见到的数据会不同。

## 6. 怎样用最短路径从第一行报错读起

先找是配置工具、编译器、链接器、launch 还是业务日志在说话。再问它当时读哪一个文件、查哪一个包、尝试了哪个动作。最后只修改能解释证据的那一层，然后重跑最短有效场景。可按这个表带读：

| 第一条明显提示 | 先回答的问题 |
| --- | --- |
| `Could not find a package configuration file` | CMake 如何找到依赖，环境加载与包安装正确吗？ |
| `fatal error: ... No such file` | 当前目标需要哪个头文件，是否是目标 ROS 版本对应的头？ |
| `... has no member named ...` | 当前对象的类型是什么，访问的是原对象还是包装？ |
| `undefined reference` | 声明已被读懂，实现有没有进这次链接？ |
| `Package ... not found` | 自建包安装和当前终端包搜索环境是否相符？ |
| `executable not found` | 包可见，具体目标是否生成和正确安装？ |
| `topic` 只有订阅或值为空 | 发布进程、解析后的名字、QoS、有效值门禁分别如何？ |
| TF 报缺变换 | 两参考系的连接和所需时刻是否能查到？ |
