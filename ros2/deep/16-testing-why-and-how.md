# 一项改动究竟怎样证明有效

这一篇深入第 24 课。你会看到，同样的“验证结果是 5”可以来自纯 C++ 数学检查、ROS 2 话题传输或已安装 launch 的整体验证。读一份测试先找输入、观测点和可证伪的断言，再判断它覆盖了什么。

## 1. 先为测试写一个可观察的承诺

以下三句都是具体的承诺：

- 当普通 C++ 计算拿到 5 米与 3 米时，水平距离等于 4 米。
- 当转换节点收到 500 厘米后，它在输出话题发一条 5.0 米。
- 当从安装区启动船的定位链，并给三路正确输入时，定位输出的参考系与 XYZ 同时符合约定。

第一句不需要 ROS。第二句依赖两个端点和执行器。第三句还依赖构建、安装和多进程启动。越靠后的检查覆盖面越广，失败时可能的原因也越多。在项目里可以同时保留不同层级。先用最小测试固定边界，再用集成测试保证各环节接在一起。

| 检查层级 | 输入从哪来 | 观察哪项结果 | 适合发现 |
| --- | --- | --- | --- |
| 数学函数 | 直接传参数 | 返回值或错误码 | 公式、单位、分支、舍入容差 |
| 状态更新 | 人工按次调用处理函数 | 是否得到结果、保留了哪项状态 | 三路缺失、零值、过期恢复 |
| 节点接口 | 模拟端经话题发布 | 接收正确类型、字段、参考系 | 订阅名、QoS、构造端点和消息填充 |
| 安装入口 | 从被安装的 launch 启动 | 各节点同时按配置工作 | 安装遗漏、重映射、依赖、融合接线 |
| 实船链路 | 设备采样或控制 | 物理量、时钟、接线和行为 | 无法由模拟代替的安装、设备与环境问题 |

## 2. 把接收方当黑盒，为什么还可以用 Python

C++ 与 Python 两个程序使用同名 ROS 2 消息接口。测试能模拟发布端，观察被测 C++ 节点的外部行为，和把测试代码写在 C++ 内部是两种方法。前者可独立检查真正的通信路径。船的 `test_localization.py` 使用 `rclpy`（ROS Client Library for Python，ROS 2 的 Python 客户端库）。当读到 `received.update({label: msg})` 时，可理解为“把这一类最新消息放入字典对应位置”。标签让同一套观察代码复用给多个话题。

本节用之前的教学包解释测试过程。程序需要 [已安装的转换节点](10-build-a-teaching-package.md)。下面 Python 程序自己启动观察端与模拟发布端，不负责启动 C++ 进程。输入使用 350 厘米，这样能分辨它与已有演示源的固定 500 厘米。验证时只启动转换节点和这个测试进程，两个进程使用相同的本机通信设置。

```python
import math
import time

import rclpy
from std_msgs.msg import Float64


def check_conversion():
    rclpy.init()
    node = rclpy.create_node('length_study_check')
    last_output = None

    def remember(message):
        # nonlocal 表示给外层函数那份 last_output 赋值。
        nonlocal last_output
        last_output = message.data

    # 两个端点都要保留在测试节点中，可通过节点的销毁一起清理。
    sender = node.create_publisher(Float64, '/study/length_cm', 10)
    node.create_subscription(Float64, '/study/length_m', remember, 10)

    seconds_to_wait = 8.0
    deadline = time.monotonic() + seconds_to_wait
    try:
        while time.monotonic() < deadline:
            # 开始时 DDS 可能还没完成匹配，因此重复发送样例。
            sender.publish(Float64(data=350.0))

            # 运行至多一段时间，让观察订阅的回调有机会处理。
            rclpy.spin_once(node, timeout_sec=0.1)

            if last_output is not None:
                # 有输出后立即判断内容。观察到了错误值就明确报错。
                if not math.isclose(last_output, 3.5, abs_tol=1e-9):
                    raise AssertionError(f'expected 3.5 m, received {last_output}')
                print('connected: 350 cm became 3.5 m')
                return

        raise AssertionError('no output on /study/length_m before the deadline')
    finally:
        node.destroy_node()
        rclpy.shutdown()


if __name__ == '__main__':
    check_conversion()
```

从执行顺序看，`create_subscription` 登记回调，之后 `spin_once` 才给它处理消息的机会。`None` 和 C++ 的空 `optional` 表达类似需求。这里用 `last_output is not None` 区分曾收到与从未收到。只写 `if last_output` 会忽略合法的 0.0。`time.monotonic()` 计算测试超时，不代表传感器采样时刻。`finally` 使函数正常完成或断言抛出后都清理测试端点。

测试报告 “no output” 和 “expected 3.5 m, received ...” 是两条不同证据。前者需要先看连接和执行器，后者说明已经有一条输出但业务结果不符合。消息可能来自其他同名发布者，因此用相同本机隔离设置且只运行所需进程。要同时支持多个测试独立运行，可以为它们选择不同通信域或独立话题。

## 3. 两种断言，不能用同一套等待逻辑

### 期待某件事发生

发布有效输入，最多等规定时长。等到消息后检查字段。若消息有时延，这种“直到成立或超时”比睡固定一秒再检查稳。timeout（超时）本身不是业务正确性条件，它帮助在等待无法完成时及时给出诊断。选择截止时间要给环境足够时间初次发现，正式代码可以将建立连接与业务等待分成两段。

### 期待某件事在一段时间内没有发生

例如深度未到齐时，不应出现位置。这里不能只在刚启动的瞬间看“还没有位置”就宣布测试通过，因为此刻缆长也可能没接上。需要先有证据表明上游至少正常启动、其他必要输入正在进入，再在观察窗口确认没有结果。船的集成测试先等原始角和标定角及母船航向出现，然后断言还没收到 pose。之后给深度，并确认能得到位置。前后两段合起来说明等待条件有效，而不只是系统没接通。

## 4. 打开船的 Python 测试，按作用找这几个位置

```text
generate_test_description
  找已安装的功能包共享目录
  包含真正的 localization.launch.xml，启用 EKF
  通知测试可以开始
      ↓
test_sensor_chain
  创建待注入话题的发布器，创建结果观察订阅
  安排 tick 周期喂入姿态、缆长与可选深度
  until 等待能观察到的特定条件，失败给实际观测
      ↓
  检查缺深度和深度恢复
  检查滤波位置、子船偏航、参考系与协方差
  检查深度边界和 IMU 角度变化
```

为什么测试要给子船非零偏航？因为单位四元数的输出可能仅仅来自位置消息中的默认占位。给一个容易分辨的方向，再断言融合里程计姿态接近该值，才能证明测试对 IMU 融合是否工作有区分力。相同原则可用于标定。测试用展开多项式独立算预期，如果直接把被测函数再调用一遍当答案，错误有可能同时出现在生产和验证两边。

### 验证位姿的每个字段分别承担什么

| 检查 | 为什么做 |
| --- | --- |
| XYZ 接近数学预期 | 几何公式和标定输入成功传到下游 |
| 时间、参考系和调试点一致 | 消息解释契约，能够按同一次计算关联 |
| 姿态占位不当作缆绳测量 | 没有向滤波宣称一个实际上未测到的朝向 |
| 协方差对角项符合设定 | 报告不确定性时写入了正确位置 |
| 滤波输出子 frame 为机体 | 消费方能正确辨认结果描述的对象 |
| 无深度等待，深度回来继续 | 订阅异步到达的控制流符合设计 |

实际测试断言覆盖其中多个检查。要补一个新断言，就把目标字段与要防止的故障写清。比如“单位换错”可用一组明确量级的输入，不应只判断值非空。

## 5. 怎样用容差避免测试理解错数学

浮点数很多十进制小数不能精确表示。`cos(π/2)` 多数实现返回接近零的残差，而不是二进制精确零。对期望 0，绝对容差说明可以接受多接近。对较大值，相对容差有助于与量级配合。测试用的容差要与目的对应。

| 值 | 较合适的检查 |
| --- | --- |
| 4.0 米的纯数学闭式输出 | 使用小容差比较，若计算过程保证精确也可明确说明 |
| 由 `sin`、`cos` 计算的小数 | 以公式和合理容差比较，而不是字符串相等 |
| EKF 收敛状态 | 允许计算时序造成的小变化，用合适时间窗和容差 |
| 坐标系字符串 | 字符串应精确匹配接口约定 |
| 新鲜度状态 | 选离阈值有明确距离的时间，再专门测等于阈值的规定 |

模拟时间可让状态检查成为确定性测试。以 500 毫秒为阈值，若采用“严格大于”就定义 500 正好可用、501 开始过期。要不要允许相等是需求选择。被测代码和断言都按同一合同，不能用睡眠抖动赌自己落在某个边界。

## 6. 改进航向初始化时，先写清验收顺序

如果计划让节点在第一帧前停发，验收故事是：

1. 航向节点已启动，订阅和定时器已经建立，给测试一段可观察时间。
2. 没有有效 IMU，输出话题还没有有效航向。
3. 给有效姿态，例如 90° 偏航，之后观察 270° 的发布。
4. 再给会映射成实际 0° 的姿态，确认能够发布真实的零。
5. 若还要求停更判定，再单独验证后续失效行为。

这能让“首帧等待”与“输出值为零”两个分支均可解释。若只断言最终 270° 正确，改动的前半部分完全没有被测试。

改定位缓存的方式类似。用合成时刻隔离条件，为缺一项、某项过期、接到无效读数、真实零值恢复各留一个不同观测。若有人建议给三格都默认 0 以让程序快点出值，测试也能捕获这个改动打破了“无深度不解算”的合同。

## 7. 做录包回放时怎么确定它验证了哪段

rosbag2（ROS 2 的录制与回放工具）可以保存选定话题里的消息。回放原始 IMU、缆长和深度，可重新走定位链。回放最终位姿，则可以只验证可视化或下游行为。不要把验证输入和计算得到的输出同时回放到同一个测试话题，除非已安排互不干扰的名字。否则实时计算和回放可能各自发布，观察者得到混合结果。

读记录时还要看保存的是消息时间、接收时间，还是两者都有。回放时倍速、暂停和仿真时间会影响超时条件。选择回放输入、命名空间与时钟，应服务于这一次要验证的因果链。这样实船上一次偶发断续也能被带回电脑逐步复现。
