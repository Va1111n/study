# 用证据定位故障，再看代码怎么改

本篇深入第 23、24 课。我们保留“看到什么 → 这能确定什么 → 下一步查哪里”的格式。一个症状可以有多个原因。目标是顺着实际链路缩小范围，直到能指出哪段程序、哪个设置或哪路设备需要核对。

## 23 · 一个定位节点没输出，从哪里开始

### 第一步 · 确定运行的程序和位置

先问“我启动的是哪一个程序”。启动输出出现 C++ 可执行进程，ROS 图里才能再确认节点和端点。只搜源文件、只看到构建完成都无法证明进程正在运行。看 `ros2 node list` 中实际名字，`ros2 node info` 给出它声明的订阅和发布。若 namespace 或重映射改过，默认 `/pose_node` 可能不是实际名字。

选择这个检查，是因为它把“程序没有启动”和“程序启动但在等待输入”分开。前者要查构建、安装与 launch，后者才看三路消息。

### 第二步 · 仔细核对每路是否有发布者

| 定位节点关心的输入 | 能从哪里供数 | 查不到发布端时怎样继续找 |
| --- | --- | --- |
| `/sensor/cable_length` | 旧缆绳电机及其驱动，或软件输入 | 查板端驱动进程、设备是否打开、消息最终名称 |
| `/sensor/cable_azimuth` | 角度标定节点 | 倒查原始角，再倒查 `/imu` 是否有效 |
| `/sensor/relative_depth` | 外部深度发布端或软件输入 | 旧备份只找到订阅，必须从运行中的旧船或配置追来源 |

`ros2 topic info -v` 能列出消息类型与每个端点。看到话题名仅代表某一端声明了它。有发布和订阅后，接着查名称、类型、可靠性。数值仍收不到时，看发布者是否实际更新。`ros2 topic echo` 打开自己的订阅；它的 QoS 也要匹配。`ros2 topic hz` 量的是这个观察端实际收到的速率，不能直接当作发布者内部循环频率。

### 第三步 · 读到消息还要进有效值门禁

假设深度发布者在更新，但读数一直为 NaN。对于中间件，它仍是一条合法的浮点消息；对于定位算法，这条数据会被 `std::isfinite` 拒绝，缓存不更新。第一次有效值尚未出现时，深度格为空。程序自然不会发位置。这个例子说明了“传输可见”和“业务接受”是两个判断。

如果深度之前有过有效值，后来一直为 NaN，旧缓存仍留着。只要缆长继续更新且三格都填过，当前实现还能发位置。处理它要区分“刚启动、无首帧”和“原来有、后来失效”。可以从状态变化处限频记录诊断，帮助观察是哪个话题使计算略过或沿用旧值。

### 用一段观测作完整推理

假设你在一个只启动计算节点的电脑上看到这组结果：

```text
节点 /pose_node 存在
/sensor/cable_length 从模拟发布端有数据 5.0
/sensor/cable_azimuth 从标定器有数据
/sensor/relative_depth 只有 /pose_node 一个订阅端
/solver/pose 可列出话题，监听一直没有消息
```

可以知道定位节点创建了订阅和发布端点，改 C++ 构造函数的优先级很低。深度这路没有发布者，符合代码中 `!depth_` 为真的分支。这时应先查谁给定位输入深度。只需要软件验证时，可以让模拟发布端提供 3.0，并观察输出。板上部署则要找到实际设备或节点，核对命名和单位。若只改成“深度默认 0.0”，你会在没有深度测量时就得到一个水面位置。这改变了接口语义，不能把出现一条消息当成故障修好。

### 方向反了，从哪头开始查

| 序号 | 看哪个位置 | 举例怎样解释结果 |
| --- | --- | --- |
| 1 | 定位输出消息本身的 XYZ 和坐标系 | 如果指向左侧时 Y 约为正，解析符合坐标约定 |
| 2 | 定位收到的标定后角 | 左侧相对船头应在本工程中取正角，发现为负就往前查 |
| 3 | 比较标定前后角度 | 标定器换零点、区间与偏角，确认改变出现在这之前还是之后 |
| 4 | 缆绳 IMU 和安装方向 | 核对轴、四元数顺序、驱动坐标协议、传感器局部向下方向 |
| 5 | 可视化工具或滤波器采用的坐标 | 消息中的 Y 已正确、画面仍反向，核对工具参考系、变换和时间 |
| 6 | 实际测量与物理状态 | 缆绳弯曲、受力和安装偏差可能让测得方向无法准确表示端点连线 |

选一个可推演的方向比在海试中盯乱跳的数值容易。先对定位节点直接提供标定后 π/2 弧度。5 米、3 米的场景应得 Y 约为 +4。若这个简单测试通过，先向上追原始角或向下追可视化，而非先在公式里改正负号。

### 已经发布过，后来位置时间一直更新

当深度停更但角度和缆长仍更新，看三类时间：

- 发布端测量的时间。
- 定位收到这项数据的时间。
- 定位生成这次结果的时间。

现有 `Float64` 输入没有原始采样时间，三路缓存也没有各自的接收时间。`/solver/pose` 里的时间只描述第三项。看到连续位姿时，可以确认解算函数重复运行。要判断深度是否仍新鲜，观察深度端是否有新消息，或扩展缓存记录。

在调试记录里把“症状”和“已确认原因”分开。例如记“10:12 深度话题停止接收，10:13 定位仍有输出”，再用代码解释触发路径。记录清楚的症状比只写“定位有 bug”更方便复现。

## 24 · 像读一段故事一样读集成测试

### 测试启动了真实入口，为什么还要写测试节点

`test/test_localization.py` 用 Python 创建一个用于验证的 ROS 2 节点。C++ 节点接受它发布的消息，就像收到物理驱动的输入。测试节点也订阅输出，从业务外部判断效果。通过同一消息契约观察结果，有助于同时检验构建安装、launch、话题类型、滤波配置与算法链路。

源码先查已安装包的共享目录，找到真正的 `localization.launch.xml`。这样如果安装规则漏掉 launch 或配置，测试会在入口暴露问题。`with_ekf=true` 让滤波链路也启动。准备好测试环境后，测试才创建消息输入和输出观察端点。

### 每个 Python 函数扮演什么角色

| 搜索的名字 | 在测试故事中的作用 | 不熟 Python 时怎样读 |
| --- | --- | --- |
| `generate_test_description` | 组装要启动的程序与测试准备信号 | 返回一份启动清单 |
| `watch` | 创建观察订阅，收到后存进 `received` | 类似 C 的回调加上下文，每个 label 对应一个槽 |
| `calibrate` | 用独立的展开式算预期标定角 | 测试用常量和公式，不调用被测 C++ 计算函数 |
| `tick` | 每次循环发当前所有模拟输入 | `depth is not None` 时才发深度 |
| `until` | 等待某个断言条件成立，超时给出观察信息 | 带截止时间的循环，不断发输入并调用 `spin_once` 处理观察回调 |
| `assertAlmostEqual` | 浮点量在允许误差内一致 | 角度和三角函数运算会有微小舍入误差 |

`received` 这个字典保留每类观测的最新值。看到 `received['pose']`，可以把它想成一个按名称取用的缓存。测试并没有为了每个断言再去启动一个程序。它通过多次输入改变场景，从同一条运行链观察结果。

### 按测试的输入变化理解每一段断言

| 场景 | 给哪些输入 | 等待或检查什么 | 回答的问题 |
| --- | --- | --- | --- |
| 缺深度 | 缆长、缆绳 IMU 和两路航向相关姿态都有，深度暂缺 | 原始角和标定角出现，母船航向按偏置变成 270°，位置尚未收到 | 上游工作且定位等待必要读数 |
| 深度到齐 | 增加深度 3 米 | 位姿与调试点出现，位置对应标定后角，Z 为 −3 | 整条输入逻辑接通，计算和发布保持一致 |
| 检查滤波 | 已有相对位置，另给子船非零偏航 | 滤波位置接近参考，姿态有子船偏航，机体参考系正确 | EKF 同时用到位置和子船姿态 |
| 深度超缆长 | 深度改为大小 6 米，缆长仍为 5 米 | X、Y 钳到零，Z 为 −6 | 负数开方保护及深度正负约定 |
| 缆绳倾斜 | 修改缆绳 IMU 四元数 | 原始角逐步接近 π/2，标定输出合理 | 姿态变化确实沿链路传到了角度话题 |

第一个断言的母船 IMU 给 90° 偏航，加上工程的 180° 偏置是 270°。第二组不是直接给定位节点 0 弧度，它让原始角 0 经过真实标定。因此 Y 为一个小的负数。测试验证的是业务完整链，不应照抄最简数学算例的 `(4, 0, -3)` 当期望。

在传感器发现异步的环境，固定只发一帧可能碰到订阅器尚未建立连接。当前测试用有截止时间的观察循环反复提供输入，并定期处理订阅回调。超时报告已经看到了哪些输出，有助于判断是上游没进来还是下游没有结果。固定等一秒再断言通常难解释机器变慢带来的偶发失败。

### 软件测试看得见什么

电脑上能确认程序在预定接口和已知输入下执行了什么。实船仍要核对驱动能否识别设备、量的是否正确、接线是否与参考系对应、实际时钟与频率是否符合假设。测试通过代表它覆盖的场景达到了约定。只写“测试通过”时，应同时知道测试喂了什么。

## 两个完整的改进推导

### 改进 A · 让航向的零值保持物理意义

现在 `heading_` 是一个消息对象，默认的 `data = 0.0` 让定时器一启动就能反复发零。若 IMU 尚未收到，这个零表示的是初始化状态。若真实航向恰为零，外部收到同样的数。原因是一个数值同时承担了“可用性”和“数值内容”两个角色。

一种接口行为是：有首个有效姿态之前不发航向；一旦取得有效姿态，继续按原有频率发布。将缓存改成 `std::optional<double>` 能表达这两个状态。转换后的数据写入缓存，定时器先 `if (!heading_)` 返回，然后创建 `Float64` 得到真正的数值并发布。下游要允许启动阶段暂时没有航向。若下游需要知道不可用的原因，也可以发布单独的诊断状态。测量后续停更，属于新鲜度问题，仍需考虑时间检查。

验收场景分三步：只启动航向节点并观察一段时间，没有 IMU 时保持等待；发一帧有效四元数能收到预期角；让输入恰好映射为真实 0° 时，确认零仍被发布。这样测试覆盖了“缺数据”和“数据为零”的差别。

### 改进 B · 给定位的三路缓存带上年龄

先设定业务预期。缆绳和深度可能有不同更新频率，允许失效的时间窗口要结合实测。缓存仍要区分首次未收到、有效、过期。可以为每路创建一个小记录，保存值和接收时刻；收消息时更新这一路，处理前对比计算时刻与接收时刻。

```text
收到有效数据 → 写值与接收时刻
计算入口 → 检查三路是否存在
         → 检查各路接收年龄是否超阈值
         → 若过期，等新读数并记录诊断
         → 若仍新鲜，继续原有公式
```

实现时把数值和时间当成一次更新，避免发生“新值配着旧时刻”。使用接收年龄时宜用不会因系统时钟向后校正而倒退的时间源。若业务希望支持仿真时间或录包回放，则应先明确使用哪类时钟以及回放行为。需求若是“三路采样时刻接近”，只比较接收时间还不够。设备时间、运算排队与网络延迟都可能使到达时刻与测量时刻差距很大，最终需要带采样时间的接口和同步约定。

验收做一个从冷启动到恢复的连续场景。先只更新两路，第三路未收到，不产出。再填第三路，产出正常。让深度停更，其他两路继续发送，超过阈值后停止更新位置。恢复深度后再次输出。测试只用同一设备模拟也能覆盖这条业务状态机。实船用多慢的频率、怎样对失效状态反馈，结合目标设备再验证。
