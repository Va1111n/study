# 仔细读懂 ROS 2 消息是什么，以及怎样设计稳定接口

本篇把第 12、19、20、22 课中容易误读的字段集中讲清。用船上的三类消息比对：一个读数、一个 IMU 测量、一个带时间与不确定性的位姿。再解释为什么有时要增加新消息，谁要为接口变化负责。

## 1. 消息类型与消息实例各指什么

假设看到两行 C++：

```cpp
using Scalar = std_msgs::msg::Float64;
Scalar reading;
reading.data = 5.0;
```

第一行只声明别名。第二行创建一个单独的对象。第三行给这次要用的实例填数。另创建 `Scalar other;` 会得到另一份字段，写 `other.data` 不会改变 `reading.data`。它与 C 中 `typedef struct { double data; } Scalar;` 再定义变量的方式很接近。

ROS 2 的接口可以由 `.msg` 等定义生成给不同语言。对于这个消息，接口声明大体就是一个 `float64 data`。C++ 用 `double` 字段表示，Python 用自己的接口对象表示，二者可以通过 ROS 2 交换符合约定的值。包里安装的消息类型同时服务 C++ 节点与 Python 测试。发布不传某个 C++ 对象的裸内存地址，发送的是中间件能理解的接口数据。

话题有多个独立属性。名字、消息类型和应用合同应同时写对：

| 允许使用同一个 Float64 的两个话题 | 数字示例 | 各自合法含义 |
| --- | --- | --- |
| `/sensor/cable_length` | 5.0 | 缆长 5 米 |
| `/sensor/cable_azimuth` | 1.57 | 标定方位约 90° 的弧度值 |
| `/sensor/relative_depth` | 3.0 | 深度 3 米 |
| `/mother_usv/imu/yaw` | 270.0 | 加过安装偏置的母船航向，度 |

类型只约束字段能放一个浮点数。接口文本和代码文档再解释单位、来源、范围和坐标。把航向重映射到缆绳角度的话题上，即使类型能匹配，也会让一个 270 度的量按 270 弧度参与计算。重映射只动名字，等不了单位转换节点的作用。

## 2. 读 IMU 消息时先划分四组数据

`sensor_msgs/msg/Imu` 中的姿态、角速度、线加速度来自同一组接口，但消费方可选不同部分。节点若只读姿态，其余字段还可以给别的消费方。典型读法：

```text
header
  stamp             这组测量的时间
  frame_id          数据表达的传感器参考系
orientation         四元数 x,y,z,w，表达姿态
orientation_covariance
angular_velocity    三个轴的角速度，通常 rad/s
angular_velocity_covariance
linear_acceleration 三个轴的线加速度，常用 m/s²
linear_acceleration_covariance
```

IMU 是 Inertial Measurement Unit（惯性测量单元）。源设备可能无法提供其中一项。ROS 的 IMU 接口约定，某组协方差数组首元素为 −1 表示对应测量未提供。姿态检查用 `orientation_covariance[0] == -1.0` 正是遵守这项约定。全零协方差按照 IMU 消息的约定表示协方差信息未知，应结合消费方自身的处理规则。它不能被当成“测量完全没有噪声”的证据。

### 头部有效却缺姿态时如何读

假设一条消息拥有新的 `header.stamp`，`angular_velocity.z` 也在更新，但 `orientation_covariance[0] = -1`。这说明那一帧包含发送者支持的其他测量，它没有提供姿态。当前缆绳节点通过四元数构造方向，发生缺姿态时就跳过本帧。为了得出可用的缆绳角，要找到能提供姿态的驱动配置或另外的姿态估计环节，而不是把缺省四元数装进已有算法。

### 为什么协方差不能直接当“三个标准差”

3×3 姿态协方差按行排列。三个对角索引是 0、4、8，对应各轴方差。其它位置描述共同变化的程度。矩阵不是一个长度为三的列表。比如第 4 个索引是第二行第二列。下游若按 0、1、2 取对角值，后两项会读到非对角位置。

有些设备以度/秒对外描述角速度。驱动输出到标准 ROS IMU 消息时，代码要按约定换算；与设备说明书对照时带上单位。举例说 90 度/秒约 1.571 弧度/秒。如果直接填 90，滤波器会把旋转速度理解得过大。

## 3. 位姿外面为什么还有两层

`geometry_msgs/msg/PoseWithCovarianceStamped` 是组合消息。它可以分成三层：

1. `Pose` 说明位置和方向。`Point` 含三个坐标，`Quaternion` 含四个旋转分量。
2. `PoseWithCovariance` 把位姿和一份 6×6 协方差放在一起。
3. `PoseWithCovarianceStamped` 再在外层加头部，提供时间和参考系。

把 `pose.pose.pose.position.x` 改成用更直观的变量名写，可以看到字段层数仍然相同：

```cpp
// 局部片段。out 是一条完整带协方差的位姿消息。
geometry_msgs::msg::PoseWithCovarianceStamped out;
auto& pose_with_uncertainty = out.pose;
auto& geometric_pose = pose_with_uncertainty.pose;
auto& relative_position = geometric_pose.position;
relative_position.x = 4.0;
relative_position.y = 0.0;
relative_position.z = -3.0;
```

三个别名都用引用，所以真正写到 `out` 内。如果改成按值初始化，一个字段副本被修改后，原消息里的数字还会保持原值。这种错误由 C++ 复制语义导致，与 ROS 2 是否交付没有关系。调试中如果日志里的局部数值正确，收到消息却显示零，可以检查赋值路径是不是通往原消息字段。

### 用索引公式读协方差

若矩阵维度是 6，按行展开的索引是 `row * 6 + column`。序号从 0 开始。

| 物理项 | 行、列 | 展开索引 | 放的量 |
| --- | --- | --- | --- |
| X 的方差 | 0,0 | 0 | 平方米 |
| Y 的方差 | 1,1 | 7 | 平方米 |
| Z 的方差 | 2,2 | 14 | 平方米 |
| Roll 的方差 | 3,3 | 21 | 弧度平方 |
| Pitch 的方差 | 4,4 | 28 | 弧度平方 |
| Yaw 的方差 | 5,5 | 35 | 弧度平方 |
| X 和 Y 的共同变化 | 0,1 及 1,0 | 1 和 6 | 同一协方差的对称位置 |

距离是米，方差是平方米。若标准差是 0.2 米，方差是 `0.2² = 0.04 m²`。填表时先分清设备给的是准确度范围、标准差还是方差。把 0.2 直接拿去当方差，滤波权重就会变。实际项目的这些协方差来自旧设置，不自动等同于当船上任一条件下测出来的噪声水平。改滤波参数应以记录、残差和测试目标为依据。

### /solver/debug_point 为什么方便读

调试点通常只带 `header` 和 `point.x/y/z`。原代码从同一次位姿结果复制头部和位置，减少阅读层数；需要融合各类不确定性时仍看位姿消息。两路输出不具有“直接比较接收时刻就必相同”的保证，因为它们各自被发布和交付。要关联同一次计算，更可靠的是对比消息里的时间、参考系和数值。

## 4. 旧消息只有一个数，想增加时间要怎么办

对现有 `Float64`，能稳定增加的是回调处理时刻，本机自己记住即可。若想传设备采样时间、单位来源或数据有效性，要选择能表达这些信息的接口。常见方向：

| 方案 | 能表达什么 | 需要核对的影响 |
| --- | --- | --- |
| 保持 `Float64`，追加本地接收时刻 | 不更改跨进程消息，能检测回调停更 | 各路采样是否同步仍未知 |
| 改成带头部的语义明确消息 | 采样时间、参考系和值可以一起传 | 发布与订阅都要理解同一类型和时钟来源 |
| 新建明确的诊断话题 | 同时提供可用状态与故障原因 | 下游需要设计数据与诊断之间的关联 |
| 为同时保留旧下游提供适配器 | 新程序可输出时间，旧程序仍消费原标量 | 要明确旧接口丢掉了哪些信息，避免重复权威发布者 |

如果确实需要自定义，接口可以独立设计成下面这样，用来说明每行做什么。它不是船当前的话题类型。

```text
# 教学设计稿 CableLength.msg，当前上游提供采样时间时才填。
std_msgs/Header header
float64 length_m
bool valid
```

字段名 `length_m` 写明物理单位，`valid` 区分设备报告测量失效，`header.stamp` 约定使用采样时刻。`frame_id` 是否用，要由量的含义决定。缆绳长度作为一段标量本身对坐标旋转不敏感；若在系统里对应某个设备位置，可用明确约定解释 frame 标签。

自定义消息在专门接口包里生成是常见做法。接口文件需要被生成工具处理，消费包声明和构建新依赖，然后两个进程都用新类型。把 `Float64` 订阅改成新类型，旧发布端仍发 Float64，不能凭名称自动兼容。可以给新接口新的话题名，迁移下游后再收敛。选择维持兼容的原因是部署中的消费者可能比源码里看到的节点更多。

## 5. 从一份接口约定推到代码、配置和测试

假设要验证新的深度输入。先从纸面把六项信息写全：

- **名字**决定从哪里收，是否经过重映射。
- **类型**决定有哪些字段。
- **单位和正负**决定怎样读每个数。
- **参考系与参考面**决定深度是从水面、母船机体还是其他基准量起。
- **频率、时间来源**决定允许使用多久。
- **无效值表达**决定丢弃、保留旧值还是明确转为故障。

代码照这些信息校验与转换。配置指定端点名称、阈值与必要的参考系。测试分别输入正常值、零值、停更、异常值和几何边界，观察业务输出，不能只靠“类型能匹配”作为接口正确的依据。

例子：上游约定以米记向下的大小，给出 3.0。定位当前将其取负绝对值得到 −3.0。若上游后来发 −3.0，代码恰好产生相同输出。但这种数值吻合无法区分“上游深度正负约定改变”。其他消费方若直接使用这条深度会受影响。调试应核对接口合同，回归测试保留两者的语义出处。

## 6. 数字看起来合理，却来源错误

用一条例子收尾。系统给出位置 `(4, 0, -3)`，Y 正好零。它有几种可能：

- 原始方位经过标定以后恰好为 0。
- 测试直接给标定后话题发了 0。
- 某停止更新的发布端此前留下最后一个 0。
- 重映射或重复发布者让其他程序发来的零进入这一路。

结果数一样，要凭发布端、话题连接、频率和时间判断是哪种情况。接口设计的目的正是让来源和含义可追。能解释从设备到字段再到计算的完整因果，比只看输出是否接近期望更重要。
