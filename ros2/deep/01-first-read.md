# 第一次读船的 ROS 2 代码

这是推荐的起点。把船仓库的 `orangpi_ros2/src/usv_localization/src/pose_node.cpp` 打开即可跟读。下面会把原文件的几个关键位置串起来，问清楚每一段**什么时候执行、读什么、改什么、把结果交给谁**。小例子是为讲解另写的。带真实函数名的位置可在源码里直接搜索。

你会先看到一整个故事，再逐步展开其中几行。第一次只需要把“准备端点 → 接收一条消息 → 存入该节点 → 等三路到齐 → 发布位置”读通。

## 1. 先认识船的问题

假设母船在水面，另一端的设备在母船下方，两个物体之间有一条缆绳。母船想知道：“它在我前方多少米、左边多少米、下方多少米？”测量设备给的是缆长、缆绳在水平面上的指向以及相对深度。定位节点把这三个量换成母船坐标系中的三维位置。

把它与一个普通 C 函数作对照。C 函数可以写成这样：

```c
/* 上层已经把三个输入凑齐，才调用 solve_position。 */
struct Position solve_position(double length_m, double azimuth_rad, double depth_m);

/* 这一行的三个数据同一时间已经可用。 */
struct Position child = solve_position(5.0, 0.0, 3.0);
```

船程序需要先解决一个更早的问题。三份输入来自不同环节，可能先到缆长，再到深度，最后才有角度。没有人能保证它们在同一个函数调用中同时抵达。所以节点里要有三格长期状态，再给每路数据安排“收到以后怎么做”的函数。**先有这项需求，才有类、订阅器、成员变量和回调。**

想象三路输入的顺序如下。表中的“空”是从该进程启动以后尚未保存测量。

| 事件 | 缆长格 | 方位角格 | 深度格 | 这个事件做完后 |
| --- | --- | --- | --- | --- |
| 程序刚启动 | 空 | 空 | 空 | 建好端点，等待数据 |
| 缆长消息来了 | 5.0 米 | 空 | 空 | 等待 |
| 深度消息来了 | 5.0 米 | 空 | 3.0 米 | 等待 |
| 方位角消息来了 | 5.0 米 | 0.0 弧度 | 3.0 米 | 算出并发布位置 |
| 缆长又更新 | 5.1 米 | 0.0 弧度 | 3.0 米 | 再算一次，角度和深度沿用缓存 |

这张表就是整篇的执行地图。源码每一行能在表里找到对应的时刻。问题“下一行在哪里”时，有时要跳到另一个函数，有时要等待另一条消息。

## 2. 把文件按用途分块

先用搜索找到这些名字。行号会随着你添加注释而变化，名字更容易定位。

| 在文件里搜索 | 这块代码管什么 | 第一次怎样读 |
| --- | --- | --- |
| `#include` | 告诉编译器需要用到哪些类型和标准库函数 | 认出 `optional`、`rclcpp` 和消息头文件 |
| `using Scalar` | 给较长的消息类型命名 | 以后看到 `Scalar` 就读作“装一个数的 Float64 消息” |
| `class PoseNode` | 定义一种 ROS 2 节点，它保留输入状态并能创建通信端点 | 先找构造函数和成员列表，建立“一个节点有哪些东西”的印象 |
| `PoseNode()` | 节点出生时建立参数、发布和订阅 | 看代码把哪个名字接到哪个缓存 |
| `subscribe_scalar` | 按给定名字订阅一种数值数据，并绑定写入位置 | 追 `latest = msg.data` |
| `publish_position` | 检查、计算、组装消息、调用发布器 | 分开看提前返回和成功分支 |
| `int main` | 操作系统启动程序后的入口 | 看“谁创建节点”“谁让回调开始运行” |

对于 C 背景的读者，文件开头的类定义就像结构体定义和函数实现，编译器先读懂它们。开始运行时操作系统进的是文件末尾的 `main`。这解释了为什么**源文件书写顺序与运行顺序不同**。

## 3. 从 main 开始走

先把原程序这一行展开读。下列代码与“构造临时的共享指针并直接交给 spin”表达了同一段启动过程，拆成两行方便看每一步的结果。

```cpp
rclcpp::init(argc, argv);                        // 初始化 ROS 2 运行环境。
auto node = std::make_shared<PoseNode>();        // 创建节点，构造函数在这里执行。
rclcpp::spin(node);                              // 等待并处理事件。
rclcpp::shutdown();                              // 离开事件循环后结束 ROS 2 环境。
```

* `rclcpp` 是 ROS Client Library for C++，意思是 ROS 2 的 C++ 客户端库。`::` 可以读成“在某个范围里找后面的名字”。`rclcpp::init` 是在 `rclcpp` 命名空间里找 `init`。
* `argc` 和 `argv` 来自 `main`，跟 C 的命令行参数写法一样。其名称来自 Argument Count（参数个数）与 Argument Vector（参数列表）。ROS 2 会用命令行参数设置节点，例如覆盖名称或传参数。
* `<PoseNode>` 告诉 `std::make_shared` 这次构造哪种对象。圆括号里没有传给构造函数的实参，所以会选择能无参调用的 `PoseNode()`。`auto` 让编译器从右边推导出 `std::shared_ptr<PoseNode>`，好比你手写那个长类型。
* `spin` 会在这儿停留。它等待能处理的事件，根据注册关系运行订阅回调。它不需要你手写“读缆长、等一会儿、读深度”的 `while` 循环。
* 停止程序以后，`spin` 返回。下次启动会创建新的 `PoseNode`，原来的三格内存随旧进程结束。要再算位置，需要三路各收到有效读数。

把它画成时间线：

```text
操作系统进入 main
  └─ init
  └─ 构造 PoseNode
      ├─ 初始化基类并设节点名
      ├─ 建立发布器
      └─ 建立订阅器，并登记将来要执行的回调
  └─ spin
      ├─ 收到第一条消息，运行一次对应回调，然后继续等待
      ├─ 收到第二条消息，运行一次对应回调，然后继续等待
      └─ 退出信号到来，返回 main
  └─ shutdown
```

## 4. 节点对象出生时发生什么

搜索 `PoseNode() : Node("pose_node")`。前面的 `PoseNode()` 是构造函数。后面的 `Node("pose_node")` 在初始化列表里，调用 ROS 2 基类的构造函数。基类把“我是一个可以创建端点的节点”这部分准备好，花括号里的代码才可以调用它提供的 `create_publisher` 和 `create_subscription`。

构造函数只做一次准备。这一点在理解 `create` 时非常重要。`create_publisher` 像建立一个带名字和类型的发送端，执行它时，定位消息还没有生成。`create_subscription` 建好接收端，并告诉 ROS 2 以后收到消息要调用什么。到了 `spin` 期间，事件才会驱动回调。

原来三行代码中的一个接线关系是 `length_sub_ = subscribe_scalar("/sensor/cable_length", length_);`。从左到右拆开：

| 部分 | 这一部分是什么 |
| --- | --- |
| `length_sub_` | 成员，保存返回的订阅器智能指针。这个成员让端点在构造结束后仍然存在。 |
| `subscribe_scalar` | 船代码自己写的函数，里面调用 ROS 2 的接口。它可以复用到其他两个输入。 |
| `"/sensor/cable_length"` | 订阅的数据流名字。发布者要在同名话题上提供匹配类型。 |
| `length_` | 这个节点对象里保存最近缆长的格子。传给右边后，回调知道把数写在哪里。 |
| `=` | 将右边函数返回的订阅器指针保存到左边成员。 |

`length_sub_` 和 `length_` 写着很像。你可以按后缀 `sub` 判断前者是负责收消息的端点。后者只有应用层的测量值。调试看见端点存在，只能说明准备工作做完了。看看成员是否收到数据，还得追实际回调。

同样的准备会做三遍，一次接缆长，一次接角度，一次接深度。它们复用一种接收格式，名字、缓存位置和单位由各自那一行确定。

## 5. 跟着一条缆长消息进入回调

假设旧缆长驱动迁移后在 `/sensor/cable_length` 发了一条 `std_msgs/msg/Float64`，`data` 字段为 5.0。当前软件测试也可以用模拟发布端提供这条消息。你在回调中看到的 `msg` 是 ROS 2 已经交给这次函数调用的消息对象。读出 5.0 发生在访问 `msg.data` 的时候。

这里先用 C 结构体想象消息。真正的类型由 ROS 2 生成。

```c
/* 这段只用来理解字段结构。 */
struct ScalarMessage {
    double data;
};
```

再看真实回调签名 `[this, &latest](const Scalar & msg)`。圆括号里的 `msg` 是**这次**的输入。方括号里的两项是**注册回调那时**要保存的上下文。这两个时刻相隔多久都可以，比如船启动 10 秒后才开始收到驱动数据。

| 名字 | 何时得到 | 在缆长事件里指什么 | 用到哪里 |
| --- | --- | --- | --- |
| `this` | 创建回调时 | 指向当前定位节点对象的指针 | 找到该对象的 `publish_position` |
| `latest` | 调用 `subscribe_scalar` 并创建回调时 | 指向 `length_` 所代表对象的引用 | 把本次 `msg.data` 写到那里 |
| `msg` | 每次消息到达并调用回调时 | 这次读到的 5.0 所在的消息 | 检查数值是否有限，取出 `data` |

这里两个 `&` 分处不同语法位置。`const Scalar & msg` 里的 `&` 表示引用类型，回调能读取消息，无需把消息复制给形参。`[&latest]` 里的 `&` 表示按引用捕获。船的辅助函数形参 `latest` 已经引用节点的成员，因此回调后续操作的是那个成员。节点和成员持续存在，才支撑这种用法。一般的短命局部变量不能照这个写法交给晚些才执行的回调。

回调先用 `std::isfinite(msg.data)` 筛掉非有限值。有效时执行 `latest = msg.data;`，再调用计算函数。如果你此时想先学一行 C++，看[如何把 msg.data 打印出来](../00-cpp-output.md)。输出语句只帮助你观察内部执行。它跟把消息发布到 ROS 话题是两条不同的输出路径。

## 6. 为什么收到 5.0 还没看到位置

打开 `publish_position`。第一件事是判断 `!length_ || !angle_ || !depth_`。`||` 和 C 一样表示逻辑或。三个成员用 `std::optional<double>`；读成“可以存一个 double，也可以暂时为空”。这里的 `!depth_` 问“深度格有没有值”。

对于曾学过 C 的人，下面是一个便于对照的状态图。

```text
optional 为空         对应 C 结构体中 has_value = false
optional 装着 0.0     对应 has_value = true、value = 0.0
optional 装着 3.0     对应 has_value = true、value = 3.0
```

在水面，0 米深度是一个可用的值。线正朝母船前方，0 弧度角也是可用的值。用单个 `double` 再写 `if (!depth)` 会把水面读数误作等待信号。这个项目增加了“有没有读数”状态，就能区分它们。

第一次只有缆长，后两格至少有一格空，函数在 `return;` 结束。这个 `return` 只退出当前 `publish_position()` 调用。回调继续走到末尾，再交回执行器。节点活着，缓存也仍在。等到其他话题有更新，执行器会再次调用对应回调。你可以对照 C 中一个 `void` 函数提前返回的写法。

没有收到位置很可能是程序按设计在等待。检查时要分清“收到一条消息”“三格都填过”“三次测量接近同一时刻”这三件事。当前源码保证到计算时每格至少有一次有效值。测量的时效性要额外处理。

## 7. 三格到齐之后，计算怎样落入消息

先用一组简单数。缆长 5 米，深度 3 米，缆绳的水平分量按勾股定理是 4 米。方位角是**标定后的** 0 弧度，水平分量全部落到前方 X，左方 Y 为 0。Z 朝上，因此 3 米水下是 −3 米。于是 `(4, 0, −3)`。

程序要发出去时创建了局部变量 `Pose pose;`。前一个大写 `Pose` 是类型别名，后一个小写 `pose` 是本次构建的消息实例。你会看到这种字段链 `pose.pose.pose.position.x`。把它按 C 的多层结构体读：

```text
局部变量 pose
├─ header
│  ├─ stamp      写计算发生的时间
│  └─ frame_id   写坐标用哪个参考系表达，默认 mother/base_link
└─ pose          这一层含位姿和它的不确定性
   ├─ pose       这一层含位置和方向
   │  ├─ position
   │  │  ├─ x =  4
   │  │  ├─ y =  0
   │  │  └─ z = -3
   │  └─ orientation
   └─ covariance
```

点号每次进入上一层对象的某个字段。两次出现 `pose` 字段是因为两种消息恰好都用了这个命名。默认坐标系名字标的是母船机体。三个数反映相对母船的位置。若观察者要看地图坐标，要用参考系变换重新算，换一个字符串只会改变它的标签。

真正发消息的调用是 `pose_pub_->publish(pose)`。`pose_pub_` 是持有发送端的智能指针，`->` 让你使用它指向的发布器对象。`publish` 拿到当前局部变量，把内容交给 ROS 2 传输；执行到此处才有消息出来。程序还会复制相同的时间、坐标系和位置到一个更简单的调试点。调试时看到这对输出，可以明白它们来自同一次计算。

## 8. 再跟一遍完整时序

```text
外部发布程序发一条 Float64(data = 5.0)
      ↓
ROS 2 匹配 /sensor/cable_length 的发布端和订阅端
      ↓
执行器调用已经登记的缆长回调
      ↓
msg.data 读出 5.0
      ↓
latest = msg.data 把 5.0 写入当前 PoseNode 的 length_
      ↓
publish_position 检查另外两格
      ├─ 有格子为空 → 结束这次计算，继续等待下一条消息
      └─ 三格都有值 → 取数 → 算 x/y/z → 填消息 → 调 publish
```

实际的 ROS 2 通信通常通过中间件把两个进程接起来。订阅回调的名字可以是匿名的，话题名字需要明确。`subscribe_scalar` 这个函数可以服务多个话题，是因为每个订阅器都保存了不同的接线配置，而不是根据回调名字识别输入。

最后看一个容易误会的时间现象。深度 3.0 米在早些时候已经进过缓存，后来深度发布端停了。这时缆长又来一帧。当前程序会用新缆长配旧深度算位置，并给位置盖上新的解算时间。这就是为什么“有新的位置”和“全部传感器刚刚更新”可能同时给出不同答案。[继续看数据为何会过期](07-debug-by-evidence.md)
