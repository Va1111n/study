# ROS 1 船的实物接口怎样接到 ROS 2

本篇展开第 21、22 课。读这一章先区分三条任务。推进让母船运动，缆绳电机管理缆绳并反馈长度，定位计算子船相对母船的位置。三个程序都可能操作“电机”或读到“姿态”，但最终作用和验证办法不同。

## 21 · 先把设备、驱动和接口摆在一起

```text
人的操作 → 手柄驱动 → 手柄话题 → 母船控制程序 → 两路 PWM → 电调与推进器

缆绳机械运动 → 编码器 → 电机控制器 → 串口 → 缆绳驱动 → 缆长话题
缆绳姿态     → 缆绳 IMU   → 驱动 → /imu → 姿态解算与角度标定
深度来源     → 深度发布端 → 深度话题
                                        上面三路 → 相对定位
```

控制信号如何送出去、读数怎样收回来、软件怎样再消费读数，是三种不同的数据方向。PWM、串口和话题不能凭名字互换。

| 层级 | 在源码里通常长什么样 | 能确认什么 |
| --- | --- | --- |
| 板上设备 | Linux 设备文件、引脚配置、系统给的访问权限 | 应用有没有机会接触硬件 |
| 设备协议 | 打开端口、设置通信参数、读写字节、解码，或写硬件信号 | 具体设备如何接收命令或返回测量 |
| 应用接口 | 发布和订阅、消息字段、参数、错误处理 | 其他节点怎样合法使用这份数据 |
| 业务算法 | 角度、缆长换算、定位、控制模式 | 算法认为输入和输出分别代表什么 |

能读应用接口不代表已确认实船接线。仅看到一个设备节点也无法确定它返回了符合协议的字节。每次升级逐层观察，可以区分故障发生在哪。

### 原母船推进的手柄链

在原 `catkin_ws` 中，找 `mz_usv` 的 `localjoy_docking.launch`，再看 `auto_pwm.cpp`。静态配置在 `mother` 命名空间启动手柄与控制节点。阅读 `auto_pwm.cpp` 时，可以先标出它监听的 `/mother/joy`，然后找它从 `axes` 取哪两个轴，再追转换后的两路输出。

典型手柄轴消息把摇杆位置表达成一个归一化数值。控制程序要把这个数映射到执行器理解的物理信号。原控制代码使用“中位加按比例偏移”，再限制最终范围。一个摇杆轴值应能指明它是左路还是右路，最后还要核对设备通道和物理引脚。PWM 是 Pulse-Width Modulation（脉宽调制），周期和高电平持续时间是两项量。ESC 是 Electronic Speed Controller（电子调速器），也叫电调。旧代码从每路 PWM 送到电调，电调再驱动推进器。推进器实际推力方向需要看接线与安装，源码里叫“左”只表示它把这路当作左侧输出。

再找模式相关的分支。遥控/自动标志、心跳、指令超时都属于应用层约定。旧程序的自动标志影响是否继续读取手柄指令，心跳丢失时有复位分支；从这份代码看，不能仅凭那个标志就确认有自动航向控制。主手动路径还要核对手柄的消息长度与停更后的应对，避免直接用固定下标或永久保留最后一次输入。看一段控制源码，可以问三个具体问题：“哪个字段改变指令？”“哪个字段表示数据已失效？”“没有新消息时，输出最终停在哪里？”

### 缆绳电机为什么走另一条路

旧 `usv/src/motor.cpp` 访问缆绳电机控制器的串口，读取反馈并计算缆长。典型编码器反馈的是轴转角或累计计数。要把它转成线长，还要确定零点、每转对应的长度、符号以及是否有减速等影响。这些是设备与机械标定信息。对定位节点来说，接口只要求 `/sensor/cable_length` 中的 `data` 以米计。驱动实现可以变化，输出契约保持一致，下游计算就可以复用。

在旧启动配置里，缆绳电机还可能订阅控制话题。阅读时明确哪条是“控制命令进入电机节点”，哪条是“长度反馈从电机节点出来”。读定位算法只需要后者。旧总入口含电机指令，软件观察选择单独的计算节点与模拟输入，免得把执行器动作混入定位验证。

设备别名 `/dev/motor` 由 Linux 设备规则配置。设备插入以后，规则根据匹配的设备属性建立可引用的名字。同一种设备重新插拔时，内核生成的序号可能变动，稳定别名有助于程序识别。升级系统后可以用旧规则当参考，核查匹配条件、实际出现的设备节点、服务用户的权限和是否有其他进程在使用端口。设备路径存在，最多说明命名环节成功。收到的字节能否解析还由串口通信设置和设备协议决定。

### 飞控、母船航向与子船 IMU 到底有什么关系

“飞控”常指通用的嵌入式控制器，具备姿态测量或控制能力，也可给船用。旧工程的母船桥接路径使用 MAVROS，让 ROS 读取 MAVLink 设备数据。MAVLink 是 Micro Air Vehicle Link（微型飞行器通信协议）。在当前 ROS 2 项目里，母船航向节点读带 `/mother` 前缀的 IMU，发布母船航向。可选的 EKF 另读子船姿态话题。母船手柄到板端 PWM 是另一条已从源码读到的控制路径。船上飞控是否也接到推进链，需要看实际接线和当次运行配置。

| 常见疑问 | 怎样用代码回答 |
| --- | --- |
| 算缆绳方向的是哪一路 IMU | 从 `imu_test1.cpp` 的订阅去找 `/imu` |
| 母船航向是否被位置节点直接使用 | 列出 `PoseNode` 的三个订阅，再看母船航向话题是否在里面 |
| EKF 为什么还要另一条 IMU | 查 `ekf.yaml` 的 `imu0` 和采纳的姿态、角速度项 |
| 改飞控安装方向影响哪一块 | 分别检查随板安装的姿态来源、下游坐标约定以及对应静态 TF |
| `relative_depth` 谁发布 | 在旧备份目前只找到订阅端，需在原系统运行时沿话题查提供方 |

## 22 · 移植旧包时保留接口含义

对照的是原 Ubuntu 20.04 / ROS 1 Noetic 与目标 Ubuntu 22.04 / ROS 2 Humble。先为每个要搬的节点写清输入、输出、参数、依赖和设备。逐项判断是“保持接口”“改为 ROS 2 写法”还是“从实船重新核实”。

### 依次走完一个节点的移植路径

以旧定位节点为例：

1. **确认应用契约。** 三路标量输入保留名称或明确重映射，标量仍用米与弧度。先记录水下 Z 为负、母船前方 X 为正等约定。
2. **迁移消息声明。** 终端类型可能从 `std_msgs/Float64` 变为 `std_msgs/msg/Float64`，C++ 命名空间也加 `msg`。字段相似时仍要重新核对头文件和值的单位。
3. **迁移节点与回调。** 旧 `ros::NodeHandle` 负责建立端点。新代码的 `rclcpp::Node` 创建端点并交给执行器。队列深度和 QoS 配置共同影响接收行为。
4. **迁移构建和安装。** 改包清单、CMake 依赖与安装规则，让新 launch 能从安装区找到节点和配置。
5. **验证软件行为。** 把原来的关键算例喂给节点，断言并检查缺输入、异常值和边界。
6. **接入一个个真实发布端。** 先测驱动从设备得到什么，再看它能否按契约发布，最后让定位综合它。硬件故障可以在进入算法之前被单独查出。

这六步的顺序有原因。从原源码抄过一个表达式只能保住一段数学逻辑。若话题名称因命名空间变了，或深度单位随着驱动改变，公式完全相同也可能没有正确结果。

### 一张可参考的接口迁移记录

| 事实 | 旧系统里从哪里确认 | 新接口要保留或验证 |
| --- | --- | --- |
| 缆长有一个数 | `usv/src/motor.cpp` 的发布处 | 单位米，有效范围，更新频率，停更如何判断 |
| 缆绳在水平面的方位 | 倾角求解和标定节点 | 标定前、后是独立话题，单位弧度 |
| 相对深度用于减去竖直边 | 旧定位订阅处 | 发布端未确认，设备来源、基准、单位和正负需要另核 |
| 母船航向有安装纠正 | 母船姿态回调与偏航处理 | 角度度数和规约区间，启动是否允许默认 0 |
| XY 位置怎样显示 | 位姿消息和旧 launch | 消息的 frame 名字，与实际坐标变换一致 |
| EKF 需要哪些分量 | 旧启动过滤设置 | ROS 2 的 YAML 掩码、各路实际安装坐标和时间 |

### 如何判断旧设备规则能不能直接继续用

系统升级后，旧规则可能继续命中同样硬件属性。板子型号一致也有利于复用。验证依据是新系统实际识别出来的设备、内核接口、启用的引脚复用和软件访问权限。引脚库中的编号、板子接线的物理脚编号和系统公开的 PWM 节点编号需要分别核对。能看到某通道文件只说明内核登记了通道，哪根线有信号要结合板端配置确认。

串口验证也按相同思路。先识别设备，后核对端口设置和协议，再让驱动独立发布测量。消息正确以后才进定位。先缓存并记录独立测量，可以复现设备事件而无需每次都运行全船。

### 旧系统与 ROS 2 同时存在时

ROS 1 和 ROS 2 使用不同的通信机制。同一个文字话题名不会自动把两端接起来。若暂时保留旧驱动，可以设计经过验证的桥接层，核对支持的消息类型、所在网络、方向和可用版本。若驱动本身也能直接迁移，则新驱动遵循相同业务契约提供给 ROS 2 计算层。选择哪一种方式主要看设备驱动支持、目标系统与可验证性。

软件包的当前状态是：四个计算节点及可选融合可在 Humble 上做软件验证。实船缆绳采集、飞控配线、深度来源、推进和停机逻辑仍需按环节确认。今后任何一项变更，都可以沿“设备 → 驱动 → ROS 接口 → 计算或控制输出”这条路径记录依据和测试结果。
