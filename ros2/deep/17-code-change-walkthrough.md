# 想改船上的一小段代码，先把影响推完

这一篇用三个具体改动练读代码的前因后果。它们是已写完的案例分析，源仓库中的节点仍按现有实现工作。案例会先说希望改变的行为，再说明改哪个入口、有谁依赖旧行为、用什么证据确认改对了。

## 案例一 · 我想知道每次收到的是哪一路数据

### 为什么只打印 msg.data 不够

在 `subscribe_scalar` 中加一行 `std::cout << msg.data`，有助于确定回调运行。但这个函数复用三次。你可能看到 5.0、0.0、3.0，碰巧顺序一变就容易猜错哪个是深度、哪个是角度。输出相同格式可支持三路，诊断需要带名称和单位。

构造时实际知道接线关系（话题参数），回调时实际知道数值（消息参数），因此可以把名字随回调保存。这里要判断捕获方式。传进函数的 `topic` 是 `const std::string&`。调用方若传字符串字面量转换成的临时字符串，它在调用表达式结束后消失。把它以引用留给长期回调会悬空。捕获一个字符串副本可以保留名称。捕获成本是创建每个订阅器时多一个较小的字符串副本，每条消息无需重新查到处找标签。

以下是与船接口形状相近的单独教学片段。它展示为什么一种数据要按值捕获、另一种按引用捕获。这里 `latest` 仍绑定活到节点销毁的成员。持有者和生命周期要由外围类提供。

```cpp
// topic 是构造订阅器时知道的字串。latest 绑定长期保存的节点成员。
// [this, &latest, topic] 会复制 topic 的内容，再为每次消息提供 msg。
return create_subscription<Scalar>(
    topic,
    rclcpp::SensorDataQoS().keep_last(10),
    [this, &latest, topic](const Scalar& msg) {
        if (!std::isfinite(msg.data)) {
            RCLCPP_DEBUG(get_logger(), "ignored non-finite input on %s",
                         topic.c_str());
            return;
        }
        latest = msg.data;
        publish_position();
    });
```

`%s` 对应 C 风格字符串指针，`c_str()` 从本次捕获保留的字符串上取得该表示。它在这次日志调用中可用。选择 `DEBUG` 级别让常规运行不必显示每次细节。高频失效仍有可能刷屏，长期设计可采用限制频率或状态变化时一次报告。

这个改动只添加证据，不改变正常数学流程。有效数据照常存储并触发解算，无效数据照常跳过。验证时选择有效三路与一条非有限数据，确认有效场景的位置不变，能在对应日志级别看到是哪路被拒绝。若有上游 remap（重映射），上面捕获的是传给创建接口的配置名。在诊断中显示最终解析名时，需要取最终端点名字或按节点的解析规则得到，不能把两者混用。

## 案例二 · 两套船程序可以在同一套 ROS 2 环境下用吗

### 为什么只给节点改一个名字不够

节点名决定通信图中可以怎么引用节点，以及参数归在哪。话题名决定消息到谁。两个节点对象即使分别叫 `pose_a` 和 `pose_b`，它们订阅源码里同一个绝对话题时，仍然会收到同一个数据流。必要的变化发生在端点名字与参数配置，而非只在 `Node("pose_node")` 字符串。

假设要在相同域同时验证 A、B 两套模拟船，每套都给一组不同数据。理想结果是：

| 系统 | 缆长 | 方位角 | 深度 | 位姿 |
| --- | --- | --- | --- | --- |
| A | `/a/sensor/cable_length` | `/a/sensor/cable_azimuth` | `/a/sensor/relative_depth` | `/a/solver/pose` |
| B | `/b/sensor/cable_length` | `/b/sensor/cable_azimuth` | `/b/sensor/relative_depth` | `/b/solver/pose` |

开始前为所有相邻程序列出解析后的名字。发现直接写绝对名就考虑显式重映射；相对名则跟所属节点的命名空间。`pose_node.cpp` 的多个名字以斜杠开头，不会因节点命名空间自动加前缀。`imu_test1` 和标定器有相对名，也要看它最终运行在哪个命名空间。混用这两种规则时，最容易发生只改一侧、导致数据断开。

### 先让一个主题走通并验证差异

可以把一套软件的 `/sensor/cable_length` 单独重映射为新名字，再让它的发布端跟上。当前输入已经统一在一个程序启动边界，启动文件可以提供参数为多条重映射传值。另一路同时继续使用原配置时，要防止历史消费者读取同时存在的数据。改接口前请先定义哪些布线是可配置的，默认值对应现有船，避免普通启动失效。

验证用不同几何结果方便分辨。A 给 5、0、3，预期前方 4 米；B 给 10、0、6，预期前方 8 米。只给 A 深度时 B 应继续等待；两边都齐时各得自己的位置。单看进程跑了两份不能证明数据隔离。要检查诊断信号和 TF 时还要独立规划参考系名称；例如两套机体若使用相同 `frame_id`，即便话题隔开，TF 对象的解释仍可能互相覆盖。

面向只在各自本机调试的临时软件场景，也可以给不同测试选独立 ROS 域或本机限定。选择取决于两套应用是否需要在同一个通信图里观测彼此。同一套真实部署的系统设计则要有明确接口约定，把名称与坐标设计写进 launch 和文档。

## 案例三 · 将公式从节点中提出来，怎么判断提取是否成功

### 找边界，先问“它需要什么才能返回”

现有节点在 `publish_position` 中混合了状态门禁、数学、消息组装和发布。这种小项目写法能让流程集中。若希望单独测试几何算法，可以提取接受三个数、返回位置的函数。它不需要知道数据来自哪个节点、不需要读取时钟，也不需要自己发布。

以[无 ROS 版本的算例](09-localization-without-ros.md)为参照，边界可以分为四项：

1. 订阅回调负责读取原消息和写节点状态。
2. 节点检查有值、有效范围和时效。
3. 几何函数只接收三项已确认输入并算结果。
4. 节点为结果选择参考系、添加时间和协方差，再发布。

保留现有行为时，注意边界条件不能无意中改变。原来深度绝对值大于缆长就把平方差钳到零，提函数时如果顺手改成提前返回，行为已改变。两项工作可以分别验证：第一步提取，输出保持；下一步才针对物理不一致的情况设计状态和策略。这样失败时能区分“拆函数少做了一步”和“业务规则按新合同变化”。

### 类型命名如何帮助读者发现单位

位置结果由数值和解释共同构成。`Point3Meters` 说明它用米；参数 `azimuth_rad` 说明角度输入用弧度。仅给字段名字不可能阻止误传类型同为 double 的数据，但至少能让调用方读出来。对输入来源繁多的系统，可以加专门类型或结构，而不是让一长串同类型按位置传递。

```cpp
// 作为接口设计片段。三个字段的意义由名字与注释共同约定。
struct CableObservation {
    double length_m;
    double azimuth_rad;
    double depth_m;
};

// 这里显式逐项赋值，避免构造时把三个 double 的位置写反。
// C++17 使用这种写法时，不依赖 C++20 的指定成员初始化语法。
CableObservation measurement{};
measurement.length_m = 5.0;
measurement.azimuth_rad = 0.0;
measurement.depth_m = 3.0;
```

如果未来希望用严格类型禁止把角度传给距离，可以为角度和距离定义各自类型，并明确转换函数。这会增加接口代码，适合多个设备、频繁混用单位的场景。项目当前规模下，清楚的变量名、校验和接口测试也是对比例足够直接的设计。复杂度应当由真实错误来源决定。

### 看一份具体的验证记录

| 旧行为断言 | 提函数后应怎样检查 |
| --- | --- |
| 三路未齐不发布 | 节点外部同时提供两路输入，确认仍无位姿 |
| 三路齐备、角度为零 | 纯数学函数得到 `(4,0,-3)`，节点接口也得到同值 |
| 深度为零合法 | 状态测试给深度 0，确认有结果 |
| 深度超缆长水平归零 | 纯计算和原节点用同样算例比 X、Y、Z |
| 时间和参考系一致 | 在输出两路对应的同一次解算查头部字段 |
| 方向变化 | 给 π/2 测 Y 正向，给 −π/2 测 Y 负向 |
| 非有限输入跳过 | 给无效一帧，确保不污染已有效缓存并不触发此次输出 |

数学函数可以用表格数据运行多组参数，端到端测试依然至少留几条关键场景。前者不用等 ROS 发现，失败比较好诊断；后者确认函数被接到了真正运行的入口。只测提取出来的新函数，不能证明每个节点实际使用了它。

## 看改动时把六项信息一起读

1. **原触发条件**：收到消息还是定时器？
2. **原状态**：哪项数据跨调用保存？
3. **新触发条件**：是否增加超时、启动等待或参数更新？
4. **接口影响**：名称、类型、单位、参考系、发布频率有没有变化？
5. **可观察证据**：哪个日志或下游能看到这个变化？
6. **覆盖证据**：软件测试与实船验证各能确认哪一段？

把这些问题分别回答，就能看清改动解决什么、是否引入新假设。讲到的三个案例给出的是工作方式，原项目若真正采用改法，应按现有运行和旧消费者进一步核对。
